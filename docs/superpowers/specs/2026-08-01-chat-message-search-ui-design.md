# 채팅 메시지 검색 UI (설계)

- 날짜: 2026-08-01
- 범위: 채팅방 화면에 메시지 검색 UI를 붙인다. 백엔드는 변경하지 않는다.
- 상태: 설계 확정 (구현 전)

---

## 1. 문제

백엔드 메시지 검색은 **완성돼 있는데 아무도 호출하지 않는다.**

- `ChatMessageController:109` — `GET /api/messages/conversation/{idx}/search` (인증 필요, 참여자 검증 포함)
- `ChatMessageService:211` → `SpringDataJpaChatMessageRepository:93` — `MATCH(m.content) AGAINST(...)`
- `frontend/src/api/chatApi.js:135` — `searchMessages` **정의만 되고 호출하는 컴포넌트가 없다**

프론트 호출부를 전수로 확인했고 0건이다. `docs/domains/chat.md §5.6`에는 기능으로 문서화돼 있으니, 빠진 건 UI 하나다.

이 상태가 만든 2차 문제도 있었다. 도달 경로가 없다 보니 `chatmessage`의 FULLTEXT 인덱스가 기본 파서로 방치돼 **2글자 한글이 0건**이었다(`시드` 30,600행 포함 → 검색 0건). `V12`가 ngram으로 전환해 고쳤다. **이 UI는 V12 위에 선다** — V12 전이었으면 검색창을 붙여도 2글자 검색이 빈 화면이었다.

## 2. 왜 이 범위인가 (대안 검토 결론)

**결과 클릭 시 동작**을 세 가지로 검토했다.

제약이 하나 있다. `ChatRoom.js:108`이 **최신 100건만 한 번에 불러오고 그 위로 더 불러오는 로직이 없다**(무한스크롤 없음). 반면 검색은 그 방의 전 기간을 뒤진다. 즉 결과가 화면에 없는 메시지를 가리킬 수 있다.

- **전체 이동** — 어떤 결과든 누르면 그 지점으로. 특정 메시지 앞뒤 구간을 불러오는 API와 메시지 목록 양방향 페이징을 새로 만들어야 한다. 작업량이 검색 UI 본체보다 크다 → 기각.
- **화면에 있는 것만 이동** — 로드된 100건 안이면 스크롤, 밖이면 불가. 백엔드 변경 0이지만 **어떤 결과는 눌리고 어떤 결과는 안 눌리는** 불규칙한 UI가 된다 → 기각.
- **목록만 표시** — 채택. "그때 뭐라고 했지"를 확인하는 용도는 이걸로 충족된다. 백엔드 변경 0, 위 제약과 충돌 없음.

**코드 배치**도 세 가지를 봤다. `ChatRoom.js`는 이미 **1,624줄**이라 이게 실제 결정이다.

- **ChatRoom.js에 그대로 추가** — 파일 하나만 건드리지만 과부하인 파일을 1,800줄로 키운다 → 기각.
- **`ChatSearchPanel.js`로 분리** — 채택. ChatRoom 추가분은 ~15줄로 묶이고, 검색은 독립적으로 테스트된다. 이 폴더는 이미 `ConversationItem`·`ChatTabs`처럼 관심사별로 쪼개는 패턴을 쓴다.
- **훅(`useMessageSearch`) + 패널** — 상태 로직을 한 겹 더 나눈다. 이 규모엔 과하다 → 기각.

## 3. 설계 결정

### 3-1. 컴포넌트 경계

신규 `frontend/src/components/Chat/ChatSearchPanel.js`.

| | |
|---|---|
| props | `conversationIdx` (number), `onClose` (fn) |
| 소유 | 검색어 입력, API 호출, 결과 배열, 로딩·에러 상태, 결과 렌더링, 하이라이트 |
| 의존 | `chatApi.searchMessages` 하나 |

패널은 **입력줄과 결과 목록을 함께** 렌더링한다. 즉 `ChatRoom`이 검색 입력을 따로 들고 있지 않는다.

`ChatRoom.js` 변경은 세 군데뿐이다 — `showSearch` 상태, 헤더 🔍 버튼, `showSearch`일 때 `<Header>` 자리에 `<ChatSearchPanel>` 렌더링. **ChatRoom은 검색이 어떻게 동작하는지 모른다.**

### 3-2. 진입·이탈

평상시 헤더는 `← 상대이름 [🔍] [⋮] [✕]`. 🔍를 누르면 헤더 자리에 패널의 입력줄이 들어서고, 패널의 결과 목록이 그 아래 메시지 영역을 덮는다(메시지 목록은 언마운트되지 않고 뒤에 남는다). ✕ 또는 Esc로 닫으면 평상 헤더로 복귀한다.

`⋮` 메뉴(나가기·삭제)에 넣지 않은 이유: 그 메뉴는 파괴적 동작만 모여 있어 성격이 다르고, 상시 검색바는 600px 모달(`ChatModal.js:120`, 데스크톱 480×600)에서 세로 공간을 계속 잡아먹는다.

### 3-3. 검색 트리거 — 제출형, 디바운스 없음

엔터 또는 🔍 클릭으로만 요청한다. 타이핑마다 FULLTEXT를 때리는 자동완성식은 넣지 않는다.

### 3-4. 2글자 미만은 요청을 보내지 않는다

`ngram_token_size=2`라 1글자는 서버가 무조건 0건을 돌려준다. 클라이언트에서 "2글자 이상 입력해주세요"로 안내하고 요청 자체를 막는다. 빈 왕복을 없애고, 사용자에게는 "결과 없음"과 "검색어가 짧음"이 구분돼 보인다.

### 3-5. 하이라이트 — innerHTML 금지

결과 본문에서 키워드를 대소문자 무시로 쪼개 `<mark>`로 감싼다. `dangerouslySetInnerHTML`은 쓰지 않는다. 메시지 본문은 사용자 입력이므로 문자열을 배열로 나눠 React가 이스케이프하게 둔다.

### 3-6. 이미지 메시지

`messageType === 'IMAGE'`면 `content`가 이미지 URL이다. 본문에 URL을 그대로 뿌리면 읽을 수 없으니 `(이미지)`로 표시한다. URL에 키워드가 들어 검색에 걸릴 수는 있으나 **표시만** 처리하고 백엔드 검색 조건은 건드리지 않는다.

### 3-7. 상태와 정렬

백엔드가 `created_at DESC`로 정렬해 주므로 프론트 정렬은 없다. 페이징도 없다(백엔드가 전건 반환).

| 상태 | 표시 |
|---|---|
| 로딩 | "검색 중..." |
| 0건 | "검색 결과가 없습니다" |
| 실패 | 패널 안 인라인 메시지 + 재시도 가능 (토스트 아님 — 패널이 화면을 덮고 있어 토스트가 가린다) |
| 정상 | "N건" + 결과 목록 (보낸사람 · 시각 · 본문) |

### 3-8. 검색 중 새 메시지

패널은 오버레이라 WebSocket 수신과 메시지 목록 갱신에 영향을 주지 않는다. 닫으면 최신 상태로 돌아온다. 결과 목록은 검색 시점 스냅샷이며 실시간 갱신하지 않는다.

## 4. 테스트

`frontend/src/components/Chat/ChatSearchPanel.test.js`. `chatApi`를 목으로 둔다.

1. 2글자 미만 제출 → API **호출 없음** + 안내 문구
2. 정상 검색 → 건수 표시 + 결과 렌더링 + 키워드가 `<mark>`로 감싸짐
3. 0건 → "검색 결과가 없습니다"

프론트 테스트 선례는 `UnifiedMap/controls/LocationControls.test.js` 하나뿐이라 그 형식(@testing-library/react)에 맞춘다.
