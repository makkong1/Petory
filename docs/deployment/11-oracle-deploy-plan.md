### 1-4. ✅ 홈 리전 결정 — **오사카(ap-osaka-1)** (2026-10-21)

🔴 **홈 리전은 무료 계정은 나중에 변경 불가.** 애초 계획은 서울(ap-seoul-1)이었으나 **가입 화면에 서울이 없었다.**

| 후보 | 결과 | 근거 |
|---|---|---|
| 서울 `ap-seoul-1` | ❌ **가입 화면 목록에 없음**(2026-10-21 실제 확인) | 2026-05 국내 후기에도 같은 보고가 있다. [Oracle FAQ](https://www.oracle.com/cloud/free/faq/)는 「원하는 데이터 리전이 없으면 인접 리전을 고르라」고 안내 |
| 춘천 `ap-chuncheon-1` | ❌ **고르면 안 된다** | [Oracle 공식 Always Free 문서](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm): **South Korea North(춘천)은 Always Free A1 프로비저닝 불가.** 고르면 12GB 를 영구히 못 쓴다(남는 건 AMD 1GB 2대 = §1-1 에서 부족 판정) |
| 도쿄 `ap-tokyo-1` | ❌ 제외 | A1 실패 후기 복수(스크립트로 하루 종일 돌려도 실패). 「서울·도쿄는 리소스 수급 문제」라는 안내도 있다 |
| **오사카 `ap-osaka-1`** | ✅ **선택** | 도쿄보다 나쁜 신호 없음(정보 공백) · **서울 다음으로 지연이 가깝다**(한국↔오사카 30ms 안팎) → 2단계 데모를 포기하지 않는다 · capacity 실패 시 **OCPU 를 낮춰 받는 우회로**가 있다 |
| 싱가포르 | 미선택 | capacity 유리 근거가 블로그 1건뿐인데 지연 70~80ms 로 **2단계를 사실상 포기**하는 선택이다 |

**일본 리전의 단점 (알고 고른 것)**
1. 지연 30ms 안팎 — **1단계(서버 안에서 k6)에는 영향 없음**(4-0-3). 2단계 데모에서 요청마다 +30ms, 포폴 수치(133→24ms)가 화면에서 54ms 로 보인다
2. 🔴 **개인정보 국외이전** — 2단계로 공개하면 고지·동의 요건이 추가된다. 1단계는 4-0-10 규칙(실데이터 미사용)으로 무관
3. 도쿄보다 낫다는 **보장은 없다** — capacity 는 운이다

⚠️ **1-3 의 「가용 도메인(AD)을 바꿔 재시도」는 성립하지 않는다.** [Oracle 공식 리전 표](https://docs.oracle.com/en-us/iaas/Content/General/Concepts/regions.htm)에서
**도쿄·오사카·서울 전부 AD 가 1개**다. 바꿀 AD 가 없다. → **실제 우회로는 OCPU·메모리를 낮춰 요청하는 것**이다
(후기 공통: 2 OCPU/12GB 가 안 되면 1 OCPU/6GB. §6 추정 메모리 합이 약 3.9GB 라 6GB 로도 기동은 된다. 받아두고 리사이즈한다)

## 2. 10번 문서에서 달라지는 것 (Fly.io → 오라클)

10번 문서의 체크 항목 중 호스트 전제가 바뀌어 **재작성이 필요한 것**만 추린다. 나머지(체크 1 CORS, 7~10 브루트포스·Refresh Token·SSE 토큰·Rate Limiting)는 호스트와 무관하므로 그대로 유효하다.

| 10번 체크 | Fly.io 전제 | 오라클에서는 |
|---|---|---|
| **2. actuator/admin-ui 노출** | "Fly가 nginx를 얇게 만들면 방어선이 사라진다" | **nginx를 그대로 쓰므로 `deny all` 블록이 유지된다.** 전제가 사라짐 — 단 블록이 실제로 동작하는지 배포 후 검증은 그대로 필요 |
| **3. 내부 포트 노출** | `[[services]]` 선언으로 제어 | compose의 `ports:`에서 mysql·redis·nlp-server·app 항목을 **제거**하고 nginx만 80/443 노출. 추가로 **OCI 보안 목록(Security List)과 인스턴스 방화벽(iptables/firewalld)에서 22·80·443만 허용** ← Fly엔 없던 단계 |
| **4. 시크릿** | `fly secrets set` | 서버의 `.env` 파일 + compose `env_file`. **이미지에 COPY하지 않는 것은 동일.** JWT_SECRET 신규 생성도 동일 |
| **5. Firebase 키** | 환경변수만 지원해 base64 우회 필요 | **파일을 서버에 직접 두고 볼륨 마운트하면 된다.** 우회 불필요 (단 §4에서 FCM 자체를 끌지 결정) |
| **6. TLS 이중 종료** | Fly edge가 TLS 종료 → nginx 443 블록 제거 | **nginx가 443을 직접 종료한다.** 443 블록을 **유지**하고 Let's Encrypt(certbot)로 인증서를 발급한다. 10번 문서의 "443 블록 제거" 지시는 **오라클에선 적용하지 않는다** |
| **MySQL 영속성** | Fly volume 필요 | compose의 `mysql_data` named volume 그대로. 호스트 디스크(200GB 무료) 안에 남는다 |

🔴 **체크 6은 지시가 정반대로 뒤집힌다.** 10번 문서만 보고 443 블록을 지우면 안 된다.

## 3. arm64 전환 — `cd.yml` (**미적용**)

레포는 public이라 GitHub가 **arm64 네이티브 러너(`ubuntu-24.04-arm`)를 무료로 제공**한다. amd64 러너 + QEMU 에뮬레이션으로 빌드하면 몇 배 느리므로 네이티브 러너를 쓴다.

적용할 변경은 3곳이다.

```diff
--- a/.github/workflows/cd.yml
+++ b/.github/workflows/cd.yml
@@
 # main 브랜치에 push되면 Docker 이미지를 빌드해서
 # GitHub Container Registry(ghcr.io)에 자동으로 올린다.
+#
+# 배포 대상이 Oracle Cloud Ampere A1(ARM64)이라 이미지도 arm64로 빌드한다.
+# public 레포라 GitHub가 arm64 러너(ubuntu-24.04-arm)를 무료로 준다 —
+# amd64 러너 + QEMU 에뮬레이션으로 빌드하면 몇 배 느리므로 네이티브 러너를 쓴다.
+# x86 서버로 옮길 일이 생기면 platforms 에 linux/amd64 를 추가한다.
 #
 # 여기까지가 지금 시점의 CD임: ...
@@ jobs.build-and-push
-    runs-on: ubuntu-latest
+    runs-on: ubuntu-24.04-arm
@@ "Build and push" 스텝
         with:
           context: ${{ matrix.context }}
           file: ${{ matrix.dockerfile }}
+          platforms: linux/arm64
           push: true
```

검증은 YAML 파싱으로 끝냈다 (`runs-on: ubuntu-24.04-arm`, `platforms: ['linux/arm64']`, 이미지 2종 유지). **실제 빌드는 돌려보지 않았다** — `main` push 또는 `workflow_dispatch`가 필요하다.

- 🔴 **관문**: `petory-nlp-server`의 `torch`·`sentence-transformers`·`kiwipiepy`가 aarch64에서 빌드되는지. `kiwipiepy`는 소스 컴파일이고 Dockerfile에 `build-essential`이 이미 있다.
- 여기서 깨지면 **nlp-server만 빼고 나머지 8개로 먼저 올린다.** `app`이 `nlp-server: condition: service_healthy`에 걸려 있으므로 그 의존도 같이 풀어야 한다 — ❓ nlp-server 없이 앱이 뜨는지, 어떤 기능이 죽는지 **미확인**.

## 4. 기능 제어 — 🔄 **2026-10-20 방향 전환**

### 4-0. 🔴 결정 (2026-10-20) — 1단계는 "공개 데모"가 아니라 "비공개 운영 + 부하 측정"이다

**아래 4-1~4-4는 「불특정 다수가 들어온다」를 전제로 쓰였다. 그 전제가 바뀌었다.**

사용자 구상(2026-10-20, 원문): *"일단 올려 근데 다른사람들은 못쓰는 그런 걸로 올리고 이제 그 사용자체는 너랑 나만 할수있게 … 너는 그냥 curl로 백엔드 로직읽고 필요한걸 보내서 … 그리고 부하같은거를 실제로 대용량 데이터를 입히고 하는거"*

| | 1단계 (지금 할 것) | 2단계 (나중에, 할 수도 안 할 수도) |
|---|---|---|
| 목적 | **제약 있는 실제 서버에서 측정을 다시 한다** | 면접관에게 보여준다 |
| 접근 | **사용자 + Claude(curl)만** | 공개 |
| 기능 제어 | **불필요 — 다 켜둔다** | 4-4 표대로 닫는다 |
| 산출물 | 배포 환경 재측정 수치, 장애 재현 기록 | 데모 URL |

🔬 **왜 기능 제어가 불필요해지는가** — 4-3의 법적 축(개인정보보호법·위치정보법·콘텐츠 책임)은 **전부 「남이 쓰기 때문에」 생기는 의무**다. 이용자가 사용자 본인뿐이면 수집되는 개인정보가 본인 것뿐이고, 올라오는 콘텐츠도 본인 것뿐이다. → **회원가입·업로드·채팅을 막을 이유가 없다. 오히려 다 켜야 측정할 게 생긴다.**

⚠️ 단 **4-2 표의 「실제로 외부와 연결되는 것」은 그대로 유효하다** — Ollama 부재(무조건 실패), Actuator 노출, 이메일·FCM·OAuth2 실제 발송, API 키 쿼터. 이건 이용자 수와 무관하므로 §5 실행 때 그대로 처리한다.

### 4-0-1. 접근 차단 방식 — **nginx Basic Auth** (IP 허용 목록 아님)

| 방법 | 사용자 | Claude |
|---|---|---|
| IP 허용 목록 (보안목록 + nginx `allow`/`deny`) | ✅ | 🔴 **불가** — Claude 샌드박스의 출발 IP가 고정이 아니다 |
| **nginx Basic Auth** (사이트 전체 앞 1겹) | ✅ | ✅ `curl -u id:pw` |

→ **Basic Auth로 간다.** 안쪽에 기존 JWT 로그인이 그대로 있으므로 2겹이고, 검색엔진 크롤링도 차단된다.

### 4-0-2. 🔴 접속 정보를 남겨둘 것 — Claude는 세션이 바뀌면 기억하지 못한다

**Claude는 대화가 새로 시작되면 이전 내용을 모른다.** 배포 후 다음 항목을 **문서나 메모리에 남기지 않으면 매번 다시 알려줘야 한다.**

- [ ] 배포 주소(도메인 또는 공인 IP)
- [ ] Basic Auth 계정 / 비밀번호
- [ ] ssh 접속 방법(키 파일 위치·사용자명·포트)
- [ ] 데모·테스트용 앱 계정(JWT 로그인용)

⚠️ **비밀번호를 git에 올리지 말 것.** 레포에는 "어디에 있다"만 적고 값은 `~/.petory-deploy` 같은 git 밖 파일에 둔다.

### 4-0-3. 부하 측정은 **서버 안에서** 돌린다

k6를 로컬 PC나 Claude 샌드박스에서 원격으로 때리면 **측정이 망가진다**:
- 인터넷 왕복 지연이 섞여 DB·애플리케이션 병목이 그 안에 묻힌다
- 가정용 회선 업로드가 먼저 병목이 된다
- Always Free **아웃바운드 10TB/월** 한도를 갉아먹는다

→ **ssh로 서버에 들어가 거기서 k6를 실행한다.** 로컬에서 하던 것과 같은 조건이 되고 네트워크 변수가 빠진다.

### 4-0-4. 배포해서 **새로 얻는 것** (로컬 측정과 뭐가 다른가)

로컬에서 이미 측정을 다 했는데 왜 또 하는지에 대한 답이다.

1. **메모리 제약이 진짜가 된다** — 2 OCPU / 12GB에 MySQL + Redis + JVM + nginx + 프론트가 전부 올라간다. 로컬 맥에서 신경 안 쓴 **버퍼풀 크기와 JVM heap을 실제로 깎아야** 하고, 안 깎으면 OOM으로 죽는다. 설정 튜닝이 강제된다
2. **디스크가 느리다** — 블록 스토리지는 로컬 SSD보다 느리다. **버퍼풀이 작고 디스크가 느린 환경에서는 인덱스 효과가 더 크게 나타날 수 있다**(깊은 페이지 페이징 133→24ms가 더 벌어질 가능성). 포폴 재료로 오히려 좋다
3. **커넥션 풀 고갈을 실제로 만들 수 있다** — 로컬에선 잘 안 터진다
4. **ARM64 재빌드**(§1-3 리스크)
5. **죽어보고 살려본다** — OOM, 로그 추적, 재기동. 로컬에선 안 생긴다

### 4-0-5. ❌ 목표에서 **제외**한 것 — 실제 유저 트래픽

실유저 트래픽은 실유저가 있어야 생기므로 우회로가 없다. **그리고 지원한 공고 중 그걸 요구한 곳이 없다**(피스챌린지 「**기본적인** 서버 운영 및 배포 경험」 / 프라임에셋 「**기본적인** 서버 운영 또는 배포 환경 **이해**」 / 디앤씨미디어 「직접 테스트하고 배포하며 **운영 이슈를 해결해** 본 분」). 신입에게 실유저 트래픽을 요구하면 그건 신입 공고가 아니다.

🚫 **커뮤니티를 만들어 유저를 모으는 안은 기각한다** — 마케팅은 개발이 아니고, 몇십 명으로는 k6 부하에 못 미치며(동시 50을 사람으로 만들려면 실유저 수백 명이 필요), 유저가 들어오는 순간 4-3의 의무가 전부 발생한다. **구직 중인 시간을 쓸 곳이 아니다.**

✅ **대체재는 부하 테스트다.** 실무에서도 신규 서비스는 유저가 없는 상태에서 k6·nGrinder로 때려보고 론칭한다. 「실제 트래픽」의 가치는 유저 수가 아니라 **예측 못 한 패턴**이고, 그건 시나리오 설계로 상당 부분 흉내낼 수 있다(랜덤 유저·몰리는 시간대·롱테일 페이지·같은 자원 동시 접근). **일부러 고장내는 건 실유저보다 낫다 — 재현이 되니 원인을 끝까지 쫓을 수 있다.**

📌 **자소서 4문단은 유지한다.** 「아직 배포해 보지 않았다」만 **「배포했고 제약 있는 환경에서 다시 측정했는데 로컬과 이렇게 달랐다」**로 바뀌고, **뒷부분(실제 트래픽은 아니다)은 그대로 둔다.** 그게 정확하고, 디앤씨미디어 평가에서 이미 강점으로 작동한다고 봤다.

### 4-0-9. ✅ 2026-10-21 결정 — 접속 정보는 "Claude 가 값을 모르게" 둔다

사용자: *「최대한 안전한 방법으로 해봐 너도 문제가 생길수있잖아」* → 맞는 전제다. 그래서 보관 위치를 고르는 문제가 아니다.

🔴 **전제: 어디에 보관하든, Claude 가 그 값을 읽는 순간 값은 컨텍스트에 들어가고 전송된다.**
Keychain 에 넣어도 꺼내면 같다. 그래서 설계 목표는 "안전한 금고"가 아니라 **"Claude 가 볼 필요가 없게"** 다.

#### ① Claude 에게 주지 않는 것 — OCI 콘솔 자격증명
**콘솔이 요금이 나오는 유일한 경로다**(4-0-7). 가입·홈 리전 지정·인스턴스 생성·MFA 설정은 **전부 사용자가 직접** 한다.
Claude 가 콘솔에 닿을 이유가 없다. 이것만으로 최악(요금 폭탄)이 설계상 차단된다.

#### ② Claude 가 값을 안 보고 쓰게 하는 것

| 용도 | 미리 저장할 곳 | Claude 가 치는 명령 |
|---|---|---|
| ssh | `~/.ssh/config` 에 `Host petory` 별칭(키 경로·사용자명·포트·IP 를 여기 적는다) | `ssh petory` |

| 앱 테스트 계정 | git 밖 파일의 환경변수 → `source` | `"$PETORY_TEST_PW"` 참조만 |

→ IP·키 경로·사용자명·포트·비밀번호를 **Claude 가 하나도 모르는 상태로 작업이 된다.**

⚠️ **Claude 가 지킬 규칙**: `curl -v` 금지(Authorization 헤더가 출력에 찍힌다) · 비밀번호 `echo` 금지 ·
`cat ~/.netrc` 금지 · 셸 트레이스(`set -x`) 금지.

#### ③ 그래도 봐야 하면 — 폐기 가능한 **전용** 자격증명으로
- **ssh 키를 Claude 전용으로 따로 발급**해 `authorized_keys` 에 추가한다. 사용자 본인 키와 분리 → 문제가 생기면 **그 한 줄만 지우면 끝**이다
- **Basic Auth 계정도 두 개**(htpasswd 는 다계정 가능). 하나는 사용자, 하나는 Claude → 폐기가 독립적이다
- 📌 **설계의 실체는 "Claude 가 절대 안 본다"가 아니라 "봐도 그 자격증명만 버리면 된다"** 다.
  명령 출력(에러 메시지 등)에 값이 섞이는 경우를 완전히 막을 수는 없다.

#### ④ 메모리·레포에 적는 것은 값이 아니라 **사용법**
- Claude 메모리: 「배포 주소는 X · ssh 는 `ssh petory` · Basic Auth 는 `--netrc`」 — **비밀번호 0**
- 레포 문서: 같은 수준. **배포 주소는 비밀이 아니다**(Basic Auth 가 앞에서 가린다) → 오히려 적어둬야 편하다
- ⚠️ Claude 메모리는 평문이고 매 세션 컨텍스트에 로드된다. **자격증명을 둘 곳이 아니다.**

#### ⑤ 지금 사용자가 할 일 — 오라클 가입 하나뿐

서버를 띄우는 것 자체는 문제가 없다. 문제는 **실제 이용자를 받는 순간** 생긴다. 포폴 데모는 이용자를 받을 이유가 없으므로, **이용자를 안 받는 쪽으로 닫으면 아래 논의 대부분이 사라진다.** 그리고 그게 제대로 운영하는 것보다 일이 적다.

> ⚠️ 아래 법령 관련 서술은 법률 자문이 아니다. **데모 모드로 가면 이 질문들에 답할 필요 자체가 없어진다**는 것이 요점이다.

## 4-A. 🔬 인스턴스 생성 전 사전조사 (2026-10-21)

사용자 지시: *「인스턴스 생성전에 먼저 블로그든 뭐든 글좀 많이 뒤져보고」*. 아래는 그 결과다.
**출처가 블로그인 항목은 그렇게 표시했다 — 공식 문서와 구분해서 읽을 것.**

### 4-A-1. ✅ 해소 — arm64 빌드(§1-3 리스크 1): **휠이 전부 있다. 소스 빌드 안 한다**

`petory-nlp-server/Dockerfile` 은 `python:3.9-slim` 이다. PyPI JSON API 로 직접 확인:

| 패키지 | cp39 aarch64 휠 |
|---|---|
| `kiwipiepy==0.18.1` | ✅ `manylinux_2_17_aarch64` |
| `scikit-learn==1.5.2` | ✅ |
| `sentence-transformers==3.1.1` | 순수 파이썬(`py3-none-any`) — 문제는 의존성 `torch` |
| `torch` | ✅ **단 2.8.0 까지만** |

🔴 **함정: `torch 2.9.0` 부터 cp39 aarch64 휠이 사라졌다.** `requirements.txt` 에 torch 가 명시돼 있지 않아
pip 해석에 맡겨져 있다. 지금은 cp39 호환 최신(2.8.0)을 집어서 되지만, **해석이 조금만 달라지면 빌드가 깨진다.**

📌 §6 의 「`torch`·`kiwipiepy` 의 aarch64 빌드 성공 여부 — 실제로 돌려봐야 안다」는 **이걸로 답이 나왔다.**

### 4-A-2. ✅ 해소 — 유휴 회수(§1-3 리스크 3): **대상이 아니다**

[공식 문서](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm): 7일간 **세 조건을 모두(AND)** 만족해야 유휴로 판정한다 —
CPU p95 < 20% **AND** 네트워크 < 20% **AND** 메모리 < 20%(**메모리 조건은 A1 shape 에만 적용**).

§6 추정 메모리 합이 **약 3.9GB / 12GB = 32%** 다 → **메모리 조건에서 이미 안 걸린다.** 4-0-6 으로 데이터를 키우면 더 안전하다.
(회수 전 Oracle 이 메일로 먼저 알리고, 회수는 삭제가 아니라 **중지**다.)

### 4-A-3. 🔴 함정 — 방화벽이 두 겹이다 (블로그 다수 + 공식)

**VCN 보안 목록(클라우드)** 과 **OS 방화벽(iptables/ufw/firewalld)** 을 **둘 다** 열어야 한다. 한쪽만 열고 막히는 게 가장 흔한 실패다.
- Oracle Linux 이미지는 **iptables 규칙이 엄격하게 깔려 있다**
- Ubuntu 이미지는 **iptables·ufw 가 얽혀 있다**는 보고, **Docker 가 iptables 를 직접 조작해 충돌**한 사례도 있다
- ⚠️ iptables 규칙은 **재부팅하면 사라진다** → `netfilter-persistent save` 등으로 저장
- ⚠️ `-I INPUT N` 이 **앞쪽 REJECT/DROP 규칙 뒤로 들어가면 무효** → `iptables -L` 로 순서 확인
- 점검 순서: ① 서비스가 `0.0.0.0` 바인딩인지(`ss -tlnp`) ② VCN 인그레스 ③ OS 방화벽 순서 ④ 재부팅 후 유지

📌 **우리는 유리하다** — 열 포트가 **22·80·443 세 개뿐**(§2). 그리고 Docker/ufw 충돌 때문에 **VCN 보안 목록을 1차 방어선으로 믿는 게 맞다.**

### 4-A-4. 🔴 함정 — 부트 볼륨이 200GB 할당을 먹는다

> ⚠️ **용어 — 「부트 볼륨」은 Spring Boot 와 아무 상관이 없다.** boot volume = **서버가 부팅하는 디스크**,
> 즉 그 서버의 하드디스크 전체다. 여기에 **운영체제 + Docker 이미지 전부 + MySQL 데이터 + 로그**가 들어간다.
> (Spring Boot jar 자체는 수백 MB 수준이라 제약과 무관하다.)
> **「블록 볼륨」**은 나중에 추가로 붙이는 디스크다. 무료 200GB 를 **이 둘이 나눠 쓴다.**


[공식](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm): 기본 **50GB** · 인스턴스 최소 **47GB** · 최대 200GB까지 키울 수 있으나
**부트 볼륨과 블록 볼륨이 합산 200GB** 다 → 부트를 200GB 로 잡으면 **추가 볼륨을 0GB 쓴다.**
- ⚠️ 4-0-6 에서 **데이터를 키우기로 했으므로 이 배분을 먼저 설계해야 한다**
- ⚠️ 커뮤니티에 **새 볼륨에 「Always Free」 라벨이 안 붙은 사례**가 있다 → 생성 시 라벨 확인

### 4-A-5. 🔴 AD 교체 우회는 불가 → **Capacity Report API + OCPU 낮추기**

오사카는 AD 1개(§1-4). 대신:
- **Capacity Report API** 로 용량을 미리 조회할 수 있고, 공개 재시도 도구들이 그걸 쓴다
- 📌 **블로그 공통 전략: OCPU 를 줄이면 성공률이 크게 오른다** — 1 OCPU 요청이 2 OCPU 보다 훨씬 잘 된다
- → **1 OCPU/6GB 로 먼저 자리를 확보하고 2/12 로 리사이즈**한다(§6 추정 3.9GB 라 6GB 로도 기동)
- 재시도 설계: 지수 백오프(TooManyRequests 회피) · **용량 부족만 재시도하고 인증·한도 오류는 즉시 중단** · 시도 전 기존 A1 사용량 조회

### 4-A-8. 🔬 모니터링 — 현재 효과는 0이다 (2026-10-21 실태 확인)

사용자 질문: *「모니터링은 어디서 하고 우리가 한 모니터링은 어떤 효과가 있는것이며 너가 뭘 할수 있음??」*

**실제로 있는 것** (`docker-compose.yml` + `monitoring/` 전수 확인)

| 서비스 | 역할 | 호스트 포트 |
|---|---|---|
| `prometheus` (`prom/prometheus:latest`) | 15초 간격 수집 | 9090 |
| `mysqld-exporter` (`prom/mysqld-exporter:latest`) | MySQL 지표 제공 | 9104(내부) |
| `grafana` (`grafana/grafana:latest`) | 보는 화면 | 3001 |

`monitoring/prometheus/prometheus.yml` 의 수집 대상은 **2개뿐**이다 — `app:8080/actuator/prometheus`(JVM·HTTP·커넥션풀), `mysqld-exporter:9104`.

🔴 **효과는 현재 0이다. 「모니터링을 구축했다」고 쓰면 부풀림이다.**
1. **켜서 본 적이 없다.** 쿼리 감사는 `performance_schema` 로 했고 Grafana 를 쓴 게 아니다
2. 🔴 **대시보드가 없다** — `monitoring/grafana/provisioning/` 에 `datasources/datasource.yml` **하나뿐**이다.
   Grafana 를 켜면 **빈 화면**이고 그래프를 직접 짜야 한다
3. 🔴 **Grafana 관리자 비밀번호가 `admin` 으로 하드코딩**돼 있다(`GF_SECURITY_ADMIN_PASSWORD: admin`).
   **배포 전 필수 변경** — 4-0-10 의 자격증명 규칙 대상이다
4. 🔴 포트 **9090·3001 이 호스트에 노출**돼 있다 → §2 대로 `ports:` 제거 대상이다

✅ **다만 배선은 돼 있다.** Actuator 가 지표를 내보내고 exporter 가 MySQL 을 긁고 Prometheus 가 수집한다.
**켜면 숫자는 쌓인다. 보는 화면만 없다.**

#### Claude 가 할 수 있는 것 — Grafana 를 보는 게 아니라 Prometheus API 에서 숫자를 뽑는 것

Claude 는 화면을 볼 수 없다. 그러나 **Prometheus 는 HTTP API(`/api/v1/query`)가 있어 PromQL 질의 결과가 JSON 으로 온다** → **읽을 수 있다.**

1. **서버 안에서 k6 를 돌리는 동안 Prometheus 를 질의해 측정 기록을 만든다.** 1단계 목적(4-0-4 「제약 있는 서버에서 측정을 다시 한다」)과 정확히 맞는다
2. 뽑을 지표:
   - **HikariCP 커넥션풀 사용/대기** ← 4-0-4 가 「로컬에선 커넥션풀 고갈이 잘 안 터진다」고 적어둔 그 지표
   - **JVM heap·GC** ← 12GB 에서 heap 을 얼마나 깎을지의 근거(4-0-4 1번)
   - **MySQL 버퍼풀 적중률·디스크 읽기** ← 4-0-6 으로 데이터를 키워 버퍼풀을 넘기면 여기서 드러난다(4-0-4 2번)
   - HTTP 요청 지연 분위수 · slow query · InnoDB 락 대기
3. **Grafana 대시보드 JSON 을 파일로 써서 프로비저닝**할 수 있다. 단 **Claude 가 볼 수 없으므로** 판단은 사용자가 한다
4. 4-0-7 의 **CPU 급증 알람**(채굴 탐지)도 여기서 겹친다 — OCI 콘솔 알람이 더 간단하지만 Prometheus 로도 잡힌다

#### ❓ 아직 안 정한 것
- **배포 후 Grafana·Prometheus 를 어떻게 보나** — 포트를 닫기로 했으므로(§2) **ssh 터널** 아니면 nginx 경로 + Basic Auth. 미정
- ⚠️ **순서**: 모니터링 3개는 메모리를 **~400MB** 더 쓴다(§6). **1 OCPU/6GB 로 시작하면 아깝다.**
  → **처음엔 모니터링 없이 올려 자리를 잡고, 2/12 로 리사이즈한 뒤 붙인다**
- `docs/deployment/07-monitoring-logging.md` 는 Fly.io 전제 시절 문서다. 이 절과 대조 필요(미확인)

---

### 4-A-7. ✅ 인스턴스 생성 전 결정 2개 — 2026-10-21 확정

1. ✅ **부트 볼륨 = 100GB** (2026-10-21 결정). 나머지 100GB 를 블록 볼륨 여지로 남긴다 —
   데이터를 키우기로 했으므로(4-0-6) MySQL 데이터가 어디까지 커질지 모른다. 부트에 200GB 를 다 몰면
   나중에 **디스크를 분리할 여지가 0** 이 된다. 기본값 50GB 는 Docker 이미지(nlp 가 torch 때문에 크다)와
   키운 데이터에 빠듯할 수 있어 늘린다.
   예상 사용: OS 5~10GB + Docker 이미지 6~10GB + MySQL 데이터(변수) + 로그
2. ✅ **OS 이미지 = Ubuntu 24.04 (ARM)** (2026-10-21 결정). Docker 자료가 압도적으로 많고 기존 compose
   방식과 가장 가깝다. Oracle Linux 는 iptables 가 더 엄격해 초기에 더 헤맨다. ufw·Docker 충돌 보고가
   있으나(4-A-3) **VCN 보안 목록을 1차 방어선으로 쓰고 열 포트가 3개뿐**이라 영향이 작다.
   ⚠️ 생성 시 **「Always Free Eligible」 라벨 확인**.

## 5. 실행 순서 (§4 확정 후)

```
0. §4 기능 제어 범위 확정                      ← 여기서 막혀 있음
1. ✅ **오라클 가입 완료 + MFA 등록 완료 (2026-10-21)** — 홈 리전 오사카(ap-osaka-1).
   MFA 는 계정 생성 직후 Oracle Mobile Authenticator 등록 프롬프트로 끝났다(오라클이 「Security Policy for
   OCI Console」 을 심고 직접 활성화하므로 4-0-7 의 수동 경로는 불필요했다).
   ❓ **남은 것: 우회 코드(bypass code) 생성** — 폰 분실 시 1인 계정은 Oracle Support 없이 복구 불가
2. A1.Flex 2 OCPU / 12GB 인스턴스 생성          [콘솔, capacity 재시도 가능성]
3. cd.yml arm64 적용(§3) → workflow_dispatch 로 빌드 검증
   └ nlp-server 실패 시 8개 구성으로 축소
4. 10번 문서 체크 1·3·4 적용 (CORS·내부 포트·시크릿)
   + §2 표대로 체크 6을 "443 유지"로 뒤집어 적용
5. 도메인 구입 + Let's Encrypt 발급 (연 1~2만원)
6. 서버에서 수동 `docker compose up` → URL 확인
7. 10번 문서 "배포 직전 최종 확인 순서"의 검증 6종 수행
8. 되면 cd.yml 에 ssh 자동배포 스텝 추가
```

1·2번은 웹 콘솔이라 수동이다. 3번은 1·2번과 **병렬로 미리 해둘 수 있다.**

## 6. 미해결 / 확인 필요

- ❓ `nlp-server` 없이 `app`이 기동되는지, 안 되면 어떤 기능이 죽는지 (compose `depends_on` + `PetIntentClient` 확인 필요)
- ❓ `torch`·`kiwipiepy`의 aarch64 빌드 성공 여부 — 실제로 돌려봐야 안다
- ❓ 12GB에 9개 서비스를 다 올렸을 때 실제 메모리 사용량. 추정치(MySQL ~700MB + JVM ~1GB + Redis ~300MB + nlp(torch) ~1.5GB + 모니터링 3종 ~400MB)는 여유가 있어 보이나 **측정 전이다**
- ❓ 유휴 회수 정책에 실제로 걸리는지 — 걸리면 대응 방법 재검토
- ❓ §4-4의 1번 선택지 (가입 완전 차단 vs 매일 리셋)
