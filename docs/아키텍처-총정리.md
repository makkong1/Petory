## 1. 전체 구조

- **레이어드 + DDD**: `Controller → Service → Repository → Entity`, 도메인별 패키지(`domain/board`, `domain/care`, ... 14개 + common). 표준 4-레이어 구조를 도메인마다 반복.
- **기술스택**: Spring Boot 3.5.7(Java 17) + MySQL 8.4 + Redis + React 19. 실시간은 WebSocket(STOMP, 채팅) / SSE(알림). 결제는 PG 미연동 내부화폐(펫코인) 시뮬레이션.
- **근거 문서**: `architecture/overview.md`(개념 정리) · `architecture/전체 아키텍처.md`(최상위 다이어그램 다수, 가장 포괄적) · `architecture/시스템_아키텍처_다이어그램.md`(위 문서와 상당 부분 중복, Mermaid 중심)

### 2-1. 도메인 순환 의존 제거 (구조 리팩토링, 2026-07-05/06)

과거 import 그래프를 추출해보니 `user`가 leaf가 아니라 **허브**(care/location/meetup/report를 역참조)였고, `statistics → care → payment → statistics` 3노드 순환이 호출부에 숨어 있었다. 성격별로 다르게 처방:

| 역방향 의존 성격 | 처방 |
|---|---|
| 읽기 집계 | `profile` 집계 계층 신설 |
| 공유 타입(enum) | `ReportActionType`을 `common`으로 추출 (user 완전 leaf화) |
| 이벤트 클래스 소유권 | `LocationSearchPerformedEvent`를 발행자(location) 소유로 이동 |
| non-critical 쓰기 | `recordPayment`를 이벤트(`AFTER_COMMIT`)로 분리 (payment→statistics 순환 해소 + money 트랜잭션 잠재버그 제거) |
| FK+money 흐름 | care↔payment는 애그리거트로 의도 유지 |

결과: 역방향·순환 엣지 6개 제거, `user`는 완전한 leaf, `statistics`는 유입 엣지 0의 순수 집계 도메인이 됨. **현재 아키텍처 상태는 이 리팩토링이 반영된 이후 기준**이다.

- **근거**: `analysis/domain-dependency-refactoring-2026-07.md` · `analysis/dependency-graph/{before,after-step1-4}-2026-07-06.txt`(diff로 효과 확인 가능)

## 3. 횡단 관심사 (Cross-cutting)

### 인증/보안
- JWT Access(15분, `jwt.access-token-expiration-ms`) + Refresh(1일, DB저장). `JwtAuthenticationFilter`가 매 요청 DB로 권한 재조회(캐시 아님 — 제재 상태 즉시 반영 위해 의도적).
- OAuth2(Google/Naver), 이메일 인증은 단일 토큰+purpose enum 통합 설계.
- 역할 계층: `USER < SERVICE_PROVIDER < ADMIN < MASTER`, `@PreAuthorize` 메서드 레벨.
- **근거**: `architecture/user/사용자 인증 및 프로필 아키텍처.md` · `architecture/user/이메일 인증 시스템 아키텍처.md` · `interview/concepts/배경/09_보안_JWT_인증.md`

### 캐싱 (Redis)
- 실제 사용처 3가지: 알림 캐시(최신 50개, TTL 24h) · 조회 캐시(`@Cacheable` — `todayStats`, `popularLocationServices`) · 이메일 인증 임시저장(TTL 24h) · NLP dedup.
- **게시글 상세 캐시는 설정만 있고 현재 비활성** — 조회수 실시간 반영 요구사항 때문에 의도적으로 제거된 상태. 문서가 "설정 존재"와 "실제 사용"을 구분해 정확히 기록.
- **근거**: `architecture/Redis_캐싱_전략.md` · `interview/concepts/면접/08_Redis_캐시.md`

### 실시간 통신
- **알림 = SSE**: `ConcurrentHashMap` 기반 emitter, query token 인증. 서버 메모리 상태라 스케일아웃 시 Redis Pub/Sub 등이 필요(현재 미구현, 한계로 명시).
- **채팅 = WebSocket/STOMP**: SockJS, 2단계 인증. `unreadCount` 원자적 증가.
- 알림 전달은 MySQL 영구저장 + Redis + SSE + FCM 4단인데, **outbox 없이 같은 메서드에서 순차 호출**돼 비원자적이라는 게 아키텍처 문서의 핵심 지적.
- **근거**: `architecture/notification/알림 시스템 아키텍처.md`(구조 요약) / `architecture/user/알림 시스템 아키텍처.md`(Java 코드 레벨 상세, 같은 주제를 깊이만 다르게 다룸) · `architecture/chat/채팅 시스템 설계.md` · `interview/concepts/면접/06_실시간통신_SSE_WebSocket.md`

### 파일 저장
- 로컬 파일시스템 + `FileTargetType` 폴리모픽 첨부, 도메인별 `syncSingleAttachment`로 연결 분리. 관리자 삭제는 DB row만 삭제(물리파일 미삭제) — 알려진 갭.
- **근거**: `architecture/file/첨부파일 저장 & 연결 아키텍처.md`

### 결제/에스크로
- 잔액 변경은 비관적 락(`findByIdForUpdate`), 에스크로는 HOLD→RELEASED/REFUNDED 상태전이. 통계 기록은 2026-07 이벤트화(AFTER_COMMIT)로 결제 트랜잭션에서 완전 분리됨(§2-1과 동일 리팩토링).
- **2026-08-08 정산 시점 재설계**: 에스크로를 거래확정이 아니라 **요청 등록 시점**에 잡는다(`provider` NULL = 상대 미정). 확정은 지급 대상 배정만 한다. 등록에 잔액 "확인"만 있고 잡지는 않던 TOCTOU를 없앤 것. 완료는 **양쪽 확인**(`POST /api/care-requests/{id}/complete`)해야 정산되며, 그 전에는 제공자가 혼자 눌러 돈을 가져갈 수 있었다. → `refactoring/care/care-settlement-integrity-2026-08-08.md`
- **근거**: `architecture/payment/펫코인 결제 아키텍처.md`

### NLP 연동 (폴리글랏)
- Spring ↔ FastAPI(petory-nlp-server) 완전 분리. signal 저장(TTL/threshold 차등), Redis dedup fail-closed 정책으로 NLP 서버 장애가 본 서비스로 전파되지 않게 격리.
- **근거**: `architecture/recommendation/반려생활 추천 & NLP 아키텍처.md` · `architecture/# Petory 한국어 케어 의도 분석 기반 주변 서비스 추천 시스템 계.ini`(초기 설계 로드맵)

## 5. 배포 아키텍처 (요약, 상세는 `deployment/`)

- Docker Compose 5컨테이너(nginx/app/mysql/redis/nlp-server), Nginx 리버스프록시. 현재는 Rolling Update, Blue-Green은 향후 과제.
- **CI/CD는 테스트·빌드까지만 구축**, 이미지 push·자동배포(CD)는 미구축 — 배포는 수동 8단계 + git checkout 롤백.
- `interview/concepts/db-infra/00_목차.md`가 지적하듯 **`deployment/` 문서 일부가 실제 Dockerfile/docker-compose보다 오래됐을 수 있음**(신뢰도 주의).
- **근거**: `deployment/README.md`, `deployment/01-deployment-strategy.md` ~ `08-troubleshooting.md`, `interview/concepts/db-infra/*`

## 6. 알려진 아키텍처 리스크 모음 (한 번에 보기)

- 알림 4단 전달(DB/Redis/SSE/FCM)이 outbox 없이 비원자적 — `architecture/notification/`
- ~~에스크로 실패가 Care 트랜잭션 롤백으로 이어지지 않음~~ → **오서술이었다.** `REQUIRED`로 합류하므로 실패는 항상 rollback-only를 남겼고, 예외를 삼켜도 바깥 커밋에서 터졌다. 2026-08-08에 삼키던 `try/catch`를 제거해 원인 예외가 그대로 전파되도록 고쳤다(HTTP 500 → 원인 명시) — `refactoring/care/care-settlement-integrity-2026-08-08.md`
- **확정 후 일방 취소**: 요청자가 `IN_PROGRESS`에서 취소하면 환불받고 제공자는 일하고 못 받는다. 분쟁 처리가 필요해 의도적으로 남김 — 같은 문서
- **충전 멱등키 없음**: 재시도로 두 번 충전된다(현재 PG 미연동 시뮬레이션) — 같은 문서
- Admin이 Facade 경로/직접호출 경로 혼재, 감사로그 커버리지 불균일 — `architecture/admin/`
- 파일 삭제 시 물리파일 미삭제 — `architecture/file/`
- SSE가 서버 메모리 상태라 수평 확장 시 별도 조치(Redis Pub/Sub 등) 필요 — `analysis/scalability-maintainability-review-2026-07.md`
- `user` 허브화 순환의존은 2026-07-05/06 리팩토링으로 해소됨(§2-1) — 과거형 리스크로만 남음
