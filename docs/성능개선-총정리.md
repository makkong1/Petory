## 1. N+1 문제 해결 — 배치 조회 패턴 ⭐⭐⭐ 최우선

### 문제 → 최신 수치 (2026-07-12 git worktree 재검증)

| 도메인 | Before | After | 효과 |
|---|---|---|---|
| Board | 301 queries / 787ms | 3 queries / 38ms | -99% |
| Care | 151 queries / 478ms | 4 queries / 210ms | -97.4% |
| Chat | 41 queries / 167ms | 4 queries / 70ms | -90.2% |
| MissingPet | 267 queries / 762ms | 4 queries / 88ms | -98.5% |

⚠️ **재검증 전 수치는 틀렸었다**: Chat `21→4`는 과소집계(참여자 조회 누락, 실제는 `41→4`), Care `~2,400`은 `@BatchSize` 도입 이전 값(현재는 `151→4`). 오래된 문서(`troubleshooting/*-n-plus-one-*.md`)의 옛 수치를 그대로 인용하지 말 것.

### 왜 이 방식인가 — Fetch Join vs `@BatchSize`, 왜 두 개를 다 쓰는가

N+1 해결책은 하나가 아니라 최소 3개가 후보다: **Fetch Join**, **`@BatchSize`(IN절 배치)**, **DTO 프로젝션 전용 쿼리**. 이 프로젝트는 상황에 따라 앞의 둘을 구분해 쓰는데, 기준은 "쿼리 특성"이 아니라 **"컬렉션 개수 + 페이징 여부"**다(`analysis/entity-schema/03-n-plus-one-strategy.md`).

| 기준 | Fetch Join | `@BatchSize(50)` |
|---|---|---|
| 쿼리 수 | 1개로 끝 | `1 + ceil(N/50)`개로 수렴 |
| 컬렉션 2개 이상 동시 조회 | **카테시안 곱** 발생(예: 댓글×첨부파일 조합 폭발) | 카테시안 곱 없음(컬렉션마다 독립 IN절) |
| 페이징(`Pageable`) | Hibernate가 메모리에서 페이징(경고 로그, 대량 로드 위험) | 페이징 그대로 DB에서 처리, 안전 |
| 선택 기준 | **단건 상세, 단일 컬렉션** | **목록/페이징, 다중 컬렉션** |

즉 "Fetch Join이 쿼리 1개니까 항상 더 좋다"가 아니라, **페이징+다중 컬렉션에 Fetch Join을 쓰면 오히려 메모리 페이징이라는 더 나쁜 문제로 바뀐다**는 게 핵심 근거. 그래서 이 프로젝트는 게시글 상세(단건)는 Fetch Join, 게시글 목록(페이징+댓글/반응/첨부 다중 컬렉션)은 `@BatchSize`로 나눴다.

**적용 패턴(공통 코드)**:
```java
// 1. ID 목록 추출
List<Long> ids = entities.stream().map(Entity::getId).collect(Collectors.toList());
// 2. 배치 조회 (IN 절)
@Query("SELECT e FROM Entity e WHERE e.id IN :ids")
List<Entity> findByIds(@Param("ids") List<Long> ids);
// 3. Map으로 변환하여 메모리에서 매핑
Map<Long, Entity> entityMap = entities.stream().collect(Collectors.toMap(Entity::getId, e -> e));
```

### 진행 과정 (측정 도구 자체를 의심해야 했던 사례)

1차로 Hibernate `Statistics.getQueryExecutionCount()`로 재검증했더니 **실제 SQL의 절반만 집계**됐다 — Spring Data 파생 쿼리와 컬렉션 lazy 초기화를 이 API가 세지 않기 때문. 측정값을 그대로 믿었다면 "N+1이 이미 없다"고 잘못 결론 낼 뻔했다. SQL 로그 카운트(`grep -c`)로 도구를 교체한 뒤에야 Chat이 실제로는 `41→4`(기존 문서엔 `21→4`로 과소집계)였다는 걸 알았다. **"수정이 안 됐다"가 아니라 "측정 도구가 절반만 봤다"는 걸 구분한 게 이 재검증의 핵심.**

재검증 중 `file` 테이블에 `(target_type, target_idx)` 인덱스가 없어 첨부 조회가 매번 풀스캔이던 것도 함께 발견 — **N+1과 인덱스는 별개 축**이라는 걸 보여주는 사례(쿼리 수를 줄여도 스캔량은 그대로일 수 있음, 인덱스 추가로 5~14배 추가 개선).

## 2. 동시성 제어 — 시나리오별 전략 의사결정 ⭐ 대표 심화 사례

### 결정 프레임워크

> **"현재 값을 읽어서 검증/분기해야 하는가?"**

| 상황 | 전략 | 이유 |
|---|---|---|
| 현재 값을 읽고 판단해야 함(잔액 부족, 두 주체 상태 조합) | **비관적 락** `SELECT … FOR UPDATE` | read-modify-write를 직렬화해야 최신 커밋값을 검증 가능 |
| 단순 조건부 증가/감소(인원<최대, 카운터+1) | **원자적 조건부 UPDATE** | 체크+변경을 DB 한 문장으로 원자화. 락 대기 없음 |
| 유일성 보증(닉네임, 소셜계정) | **DB Unique 제약** | 앱 레벨 사전 체크는 TOCTOU라 못 막음. DB가 최종 보증 |
| 부분 실패 시 전체 롤백 | **트랜잭션 경계** | 원자적 커밋/롤백 |

### 왜 이 방식인가 ① — Meetup 참가 인원: 5가지 대안을 실제로 비교한 근거

인원 초과를 막는 방법은 하나가 아니다. 실제로 5개를 코드 레벨까지 비교했다(`troubleshooting/meetup/race-condition-participants.md`):

| 방식 | 분산환경 | 동시성 | 복잡도 | 채택 여부 |
|---|---|---|---|---|
| 세마포어(메모리) | ❌ 서버별 독립, 재시작 시 소실 | 빠름 | 낮음 | 기각 |
| 비관적 락 | ✅ | 락 대기로 블로킹, 데드락 위험 | 낮음 | 기각(§②에서 이유 상세) |
| 낙관적 락(`@Version`) | ✅ | 충돌 시 재시도 필요, 여전히 재시도 로직 복잡 | 중간 | 기각 |
| Redis 분산 락 | ✅ | 빠름 | 인프라 의존(Redis 운영비용) | 기각 |
| **원자적 조건부 UPDATE** | ✅ | 락 대기 없음 | **가장 단순** | **채택** |

**Before(문제 코드)**:
```java
if (meetup.getCurrentParticipants() >= meetup.getMaxParticipants()) {
    throw new RuntimeException("모임 인원이 가득 찼습니다.");
}
// 여기서 다른 트랜잭션이 끼어들 수 있음 — check와 write 사이에 gap
meetup.setCurrentParticipants(meetup.getCurrentParticipants() + 1);
meetupRepository.save(meetup);
```

**After(채택한 방식)**:
```java
@Modifying
@Query("UPDATE Meetup m SET m.currentParticipants = m.currentParticipants + 1 " +
       "WHERE m.idx = :meetupIdx AND m.currentParticipants < m.maxParticipants")
int incrementParticipantsIfAvailable(@Param("meetupIdx") Long meetupIdx);

int updated = meetupRepository.incrementParticipantsIfAvailable(meetupIdx);
if (updated == 0) throw new RuntimeException("모임 인원이 가득 찼습니다.");
```

**선택 이유(우선순위 순)**: ① 프로젝트 일관성(Chat/User 도메인의 원자적 UPDATE 패턴과 통일) ② 락 대기 없이 병렬 처리 가능 ③ 재시도 로직이나 Redis 같은 별도 인프라 불필요 ④ DB CHECK 제약(`chk_participants`)을 이중 안전망으로 추가해 앱 로직을 우회하는 직접 SQL에도 대응.

### 왜 이 방식인가 ② — "빠르니까"가 아니라는 걸 실측으로 증명

같은 문제(인원 초과 방지)를 원자적 UPDATE와 비관적 락 둘 다로 풀 수 있다. "원자적 UPDATE가 락 대기 없어 더 빠르다"는 통념을 실제로 벤치마크했더니:

| 방식 | 평균 | 최소 | 최대 |
|---|---|---|---|
| 비관적 락 | **2.40ms** | 1ms | 7ms |
| 원자적 UPDATE | **8.40ms** | 6ms | 13ms |

**저경합·소량 데이터에선 비관적 락이 오히려 더 빨랐다.** 그래서 원자적 UPDATE를 고른 진짜 이유는 latency가 아니라 **락/데드락 관리 부담 제거 + 코드 단순성 + 참가자 INSERT까지 락을 붙잡고 있지 않음**이라는 걸 데이터로 재확인했다(고경합 확장성 우위는 이론적 근거일 뿐, 이 벤치마크로 입증된 건 아니라고 명시). 이게 "속도 때문에 골랐다"는 안일한 답 대신, **측정으로 자기 통념을 반증한** 근거가 된다.

### 왜 이 방식인가 ③ — PetCoin은 왜 원자적 UPDATE가 아니라 비관적 락인가

같은 "동시성 문제"인데 Meetup과 다른 전략을 쓴 이유: PetCoin의 `deductCoins`는 **"잔액이 충분한가"를 판단**해야 한다. 원자적 UPDATE(`WHERE balance >= amount`)로도 표현은 가능하지만, 이 프로젝트는 차감 실패 사유(부족 vs 존재하지 않음 등)를 세밀하게 분기해야 해서 **현재 값을 읽어서 판단하는 비관적 락**을 택했다 — 결정 프레임워크의 첫 줄("현재 값 검증이 필요한가")이 그대로 적용된 사례.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT u FROM Users u WHERE u.idx = :idx")
Optional<Users> findByIdForUpdate(@Param("idx") Long idx);
```

Care 거래확정도 마찬가지로 "요청자·제공자 둘 다 확정했는가"라는 **두 주체 상태를 함께 판단**해야 해서 비관적 락(상위 엔티티 `Conversation`)을 썼다 — 흥미로운 건 원인이 "중복 실행"이 아니라 **REPEATABLE READ 격리수준 때문에 서로의 미커밋 확정을 못 봐 로직이 skip되는 stuck state**였다는 점. "동시에 두 번 실행돼서"가 아니라 "격리수준이 판단 시점의 정합성을 깨서" 생긴 버그라는 걸 원인 분석에서 밝혀낸 게 핵심.

## 4. 근처 검색 — B+Tree에서 R-Tree(공간 인덱스)로, 4세대에 걸친 진화

Meetup의 "근처 모임 조회"는 한 번에 지금 구조가 된 게 아니라, 문제를 하나씩 걷어내며 4세대를 거쳤다. **이 진행 과정 자체가 "왜 이 방식인가"에 대한 답**이다.

| 세대 | 방식 | 문제/한계 | 결과 |
|---|---|---|---|
| Gen1 | 전체 로드 후 Java `Haversine` 계산 | O(n) 메모리·시간, 데이터 늘면 선형 악화 | 스캔 2,958행, 486ms |
| Gen2 | DB Bounding Box(`BETWEEN` 위경도) | 조건 순서·서브쿼리 방식은 인덱스를 못 탔음(먼저 2번 실패) | 스캔 117행(-96%), 273ms(-43.8%) |
| Gen3(현재) | 공간 인덱스 `ST_Within`(POLYGON)+`ST_Distance_Sphere` | 옵티마이저가 현재 데이터량에선 여전히 date 인덱스를 고름(아래 설명) | 구조적으로 대비 완료 |

### 왜 Gen2(Bounding Box)가 처음부터 성공한 게 아니었나

`refactoring/meetup/nearby-meetups/index-analysis.md`에 실패 이력이 남아있다: ① 조건 순서 재배치 → 인덱스 미사용 ② 서브쿼리 방식 → 인덱스 미사용 ③ **`BETWEEN`으로 바꾸고 `IS NOT NULL` 조건을 제거하니 인덱스 사용 성공.** 즉 "인덱스를 만들었는데 왜 안 타지"를 실제로 겪고 원인(조건 형태)을 고쳐서 해결한 사례.

### 왜 Gen2에서 멈추지 않고 Gen3(공간 인덱스)로 갔나 — 2D 가지치기 vs 1축 가지치기

Gen2의 `(latitude, longitude)` 복합 인덱스는 **B+Tree라 1차원 정렬 구조**다. `lat BETWEEN`은 인덱스로 좁히지만, 그 위도 밴드 안에서 `longitude BETWEEN`은 인덱스가 아니라 **사후 필터링(ICP)**으로 처리된다 — EXPLAIN이 `range`인데도 117행이나 스캔한 이유. 반면 R-Tree(공간 인덱스)는 **위도·경도 2축을 동시에 가지치기**한다.

| # | 기준 | B+Tree 복합(Gen2) | 공간 인덱스 R-Tree(Gen3) |
|---|---|---|---|
| 1 | 차원 가지치기 | 위도 1축만, 경도는 사후 필터 | 위도·경도 2축 동시 |
| 2 | **확장성(밀도↑)** | 위도 밴드 내 행 급증 → 선택도 악화 | 후보 수가 질의 박스 **면적**에 비례 |
| 3 | 의미적 정확성 | 평면 근사(111km/도) | SRID 4326 구면 거리 |
| 4 | 옵티마이저 견고성 | 컬럼 순서·`IS NOT NULL`·함수래핑에 취약(Gen2가 이미 2번 실패한 이유) | 공간 전용 술어라 안정적 |
| 5 | 확장 여지 | 점 조회 한정 | 폴리곤(행정구역) 등으로 확장 가능 |

핵심은 **2번(확장성)**: 소규모 데이터에선 Gen2도 충분하지만, 서울처럼 같은 위도대에 데이터가 넓게 퍼지면 B+Tree는 위도 밴드 전체를 긁어 선택도가 무너지고, R-Tree는 질의 박스 면적에만 비례해 버틴다.

### 정직한 부분 — 지금 옵티마이저는 실제로 공간 인덱스를 안 고른다

EXPLAIN ANALYZE 실측: 현재 데이터량에서는 `date > NOW()` 조건이 이미 극도로 선택적(`rows=1` 추정)이라, 옵티마이저가 `idx_meetup_date` B+Tree 경로를 더 싸다고 판단해 공간 인덱스 대신 그쪽을 고른다. **이건 버그가 아니라 비용 기반 옵티마이저의 정상 판단**이며, 문서도 이걸 숨기지 않고 "현재는 즉효 최적화가 아니라 데이터 규모·밀도 증가에 대비한 **선제적 구조 결정**"이라고 정직하게 적어뒀다. 데이터가 늘어 `date` 필터의 선택도가 떨어지면, 그때부터 `ST_Within`이 가장 선택적인 필터가 되어 옵티마이저가 전환할 여지가 생긴다.

## 5. NLP 기반 반려생활 의도 분석 추천 ⭐⭐

### 왜 동기 호출이 아니라 이벤트 기반 비동기인가

가장 단순한 구현은 사용자 요청 안에서 바로 NLP 서버를 호출하는 것이다. 이 프로젝트가 그렇게 하지 않은 이유는 두 가지 리스크 때문:

1. **응답 지연**: 임베딩·형태소 분석 같은 무거운 연산을 요청 경로에 넣으면 사용자가 그 연산이 끝날 때까지 기다려야 한다.
2. **장애 전파**: NLP 서버(별도 FastAPI 프로세스)가 느려지거나 죽으면, 동기 호출 구조에서는 본 서비스 API까지 함께 느려지거나 실패한다.

그래서 활동 이벤트를 `@TransactionalEventListener(AFTER_COMMIT)`(커뮤니티/케어)·`@EventListener`(위치검색)로 받아 **전용 스레드풀**(core 2/max 6/queue 500, `DiscardWithWarnPolicy`)에서 처리한다 — 사용자 요청은 이벤트 발행 즉시 끝나고, NLP 호출은 그 뒤에 별도 스레드에서 일어난다. 추가로 NLP 전용 `RestTemplate`에 **timeout 3초**를 걸고 실패 시 `Optional.empty()`로 **fail-closed** 처리해 NLP 서버 장애가 추천 기능 저하로만 끝나고 본 서비스로 전파되지 않게 격리했다.

- **근거**: `핵심성과_분석.md` §5 · `architecture/recommendation/*` · `refactoring/petRecommendation/*`

## 6. 도메인 순환 의존 제거 (아키텍처 리팩토링) ⭐⭐

### 왜 "전부 이벤트로 바꾸자"가 아니라 성격별로 다른 처방을 썼나

역방향 의존 6개를 다 같은 방법(예: 전부 이벤트화)으로 풀지 않은 이유는, 의존이 생긴 **성격이 서로 달랐기 때문**이다.

| 역방향 의존 성격 | 처방 | 왜 이 처방인가 |
|---|---|---|
| 읽기 집계(user가 care/location/meetup 데이터를 읽기만 함) | `profile` 집계 계층 신설 | 쓰기가 아니라 읽기 조합이라, 트랜잭션 정합성 이슈 없이 계층만 분리하면 됨 |
| 공유 타입(enum) | `ReportActionType`을 `common`으로 추출 | 값 하나를 공유하는 것뿐이라 이벤트/계층 분리보다 타입 이동이 더 단순 |
| 이벤트 클래스 소유권 | `LocationSearchPerformedEvent`를 발행자(location) 소유로 이동 | "이벤트는 발행하는 쪽이 소유한다"는 원칙만 지키면 되는 문제라 이벤트화가 아니라 소유권 이동 |
| **non-critical 쓰기**(통계 기록) | `PaymentRecordedEvent` + `AFTER_COMMIT` 이벤트화 | 여기가 유일하게 "동기 트랜잭션 결합이 실제 버그(통계 실패→코인 지급 롤백)를 만드는" 케이스라 이벤트화가 정당함 |
| 데이터 모델 FK + money 흐름(care↔payment) | 애그리거트로 수용(그대로 둠) | money 흐름은 트랜잭션 정합성이 필수라, 억지로 분리하면 오히려 위험 |

**"모든 순환을 이벤트로 없앤다"가 아니라, money 흐름처럼 트랜잭션이 필수인 의존은 의도적으로 남겨두고, non-critical한 것만 골라 이벤트화**한 것이 이 리팩토링의 핵심 판단이다. 결과: 역방향·순환 엣지 6개 제거, `user`는 완전한 leaf, `statistics`는 순수 집계 도메인.

- **근거**: `핵심성과_분석.md` §6 · `아키텍처-총정리.md` §2-1

## 7. 전체 쿼리 감사 — 실제 API 호출 기반 재측정 ⭐⭐⭐ 대표 심화 사례

### 왜 "SQL 직접 실행"이 아니라 "API를 curl로 호출"해야 하는가

가장 직관적인 측정 방법은 의심되는 SQL을 MySQL 클라이언트에서 직접 실행해보는 것이다. 이 프로젝트가 그 방법으로 놓친 사례가 있다: board 목록 쿼리를 튜닝하고 "0.17s→0.00s"로 끝났다고 판단했는데, 실제 API를 호출해보니 `Page<>`가 자동으로 붙이는 COUNT 쿼리(180,003행/141ms)가 존재 자체를 몰랐던 채로 남아있었다. **손으로 실행한 SELECT는 앱이 실행하는 것과 같았다 — 틀린 건 SQL이 아니라 측정 범위였다.** SQL을 직접 실행하면 "내가 떠올린 쿼리"만 측정하게 되고, ORM이 자동으로 붙이는 COUNT나 지연 로딩이 추가하는 쿼리는 애초에 측정 대상에 들어오지 않는다. 그래서 이후 감사는 전부 `curl`로 실제 엔드포인트를 호출하고 `performance_schema`로 애플리케이션이 실제 실행한 쿼리를 관측하는 방식으로 전환했다.

### 결과 요약 (12개 도메인, 엔드포인트 62개 실호출)

| 엔드포인트 | Before | After |
|---|---|---|
| care 검색(공개+관리자) | HTTP 500(항상 실패) | 200 |
| 관리자 케어요청 목록 | 66쿼리 | 7쿼리 |
| `/api/pets/type/DOG` | 7,667건·155쿼리·331ms | 20건·5쿼리·37ms |
| 모임 검색 | 500건·53쿼리·583ms | 20건·6쿼리·43ms |
| 관리자 사용자 목록 | 10,021행 검사+filesort | 20행 |
| care 주변검색 | 3,000행 풀스캔(선택도 208배 오판) | 208행(SPATIAL) |

### 이 방법론으로만 드러난 세 가지 (왜 이전 방법으론 못 봤는가)

① **기능 버그를 성능 조사 중 먼저 발견**: care 검색이 FULLTEXT 인덱스 없이 `MATCH()`를 써서 데이터 양과 무관하게 항상 HTTP 500이었다. API를 실제로 호출했기 때문에 드러났다.
② **N+1처럼 보인 게 정상 동작이었다**: 모임 검색에서 참가자 조회가 10회 나가 N+1로 의심했지만, 결과 500건 ÷ `@BatchSize` 50 = 10회로 숫자가 정확히 맞았다. 여기서 "N+1이다"라고 성급히 판단했다면 **정상 작동하는 배치 로직을 되돌리는** 실수를 했을 것 — 진짜 원인은 검색에 페이징이 없어 500건을 통째로 읽고 있던 것.
③ **측정 도구 자체가 4번 틀렸다**: `SUM_LOCK_TIME`은 행 락을 안 잡음, `DIGEST_TEXT`는 1024자에서 잘려 `FROM` 절도 못 봄, `getQueryExecutionCount()`는 지연 로딩을 누락(§1과 동일 함정), Gradle `test`는 DB 상태 변화를 인식 못해 `cleanTest`가 필요했음.

### 검증 방법 — "고쳐졌다"만으론 부족한 이유

수정 전 상태에서 테스트가 실제로 실패하는지 먼저 확인한 뒤 수정 후 통과를 확인하는 순서를 지켰다. 이 순서를 생략하면, 애초에 아무것도 검증하지 않는 테스트가 "통과" 상태로 계속 남는다 — 실제로 위의 측정 도구 문제 세 건이 이 과정에서 드러났다. 또한 쿼리 수 상한만 걸면(예: "20개 미만") 결과가 10건일 때만 우연히 통과하는 테스트가 되므로, `size`를 바꿔가며 **증가분이 결과 건수에 비례하지 않는지**를 확인하는 방식으로 검증했다.

- **측정 못 한 범위(명시적으로 "미측정")**: 자동생성 COUNT 16건, board 깊은 페이지(§8), 락 경합(단일요청 방식 한계 — 경합 자체는 동시성 부하테스트가 별도로 필요), 스케줄러 8건, notification·file(시드 없음).

## 8. 확장 사례 (포폴 refactoring 9섹션 중 나머지 — `핵심성과_분석.md`엔 아직 미승격이지만 근거는 충분함)

### 보안/인가 정리 — "패턴을 고쳤다"와 "그 패턴이 있는 모든 곳을 고쳤다"는 다르다

**1차 (2026-04-14)**: Care/Payment `@PreAuthorize` 누락 3건·IDOR 1건·소프트삭제 미체크 등 Critical 6건 수정완료. Chat은 IDOR(userId/senderIdx 클라이언트 파라미터)·참여자 검증 부재·`REQUIRES_NEW` self-invocation 개선완료. User는 제재 우회 6건 중 5건 해결.

**2차 (2026-07-14, 전체 쿼리 감사 중 발견 — 1차와는 별개 사건)**: 1차 때 이미 "클라이언트가 넘긴 userId를 신뢰하면 안 된다"는 원인을 정확히 알고 있었는데도, 같은 패턴이 `GET /api/boards/my-posts`와 `GET /api/activities/my`에 그대로 남아 있었다. `my-posts`는 파라미터를 빼면 400이 아니라 500이 나갔고, 남의 `userId`를 넣으면 그 사람 글이 그대로 조회됐다. `activities/my`는 더 나빴다 — `@PreAuthorize`조차 없이 `SecurityConfig`의 `/api/**` catch-all에만 기대고 있어서, 로그인한 누구나 남의 활동 내역(게시글·케어요청·댓글) 전체를 읽을 수 있었다. 재현: `seed_user_1`로 로그인해 `GET /api/activities/my?userId=1663`을 호출하면 수정 전엔 `seed_user_2`의 활동 21건이 그대로 나왔음(본인은 20건). 둘 다 `@AuthenticationPrincipal`에서 대상을 가져오도록 수정.

**왜 1차 때 못 잡았나**: 원인을 안다고 그 패턴이 있는 모든 곳을 찾은 건 아니라는 것 — 1차 때 고친 뒤 전 컨트롤러에서 "클라이언트가 보낸 사용자 식별자를 받는 자리"를 전수 조사(grep)하지 않았다. 2차에서는 이 전수조사를 실제로 해서, user 도메인(`PetController`·`UserProfileController`)은 전부 `@AuthenticationPrincipal`을 쓰고 있어 깨끗함을 확인했다.

### 알림 읽음 처리 최적화
- 전체읽음 102개 statement(row-by-row UPDATE) → JPQL bulk UPDATE 1개(-99%). row-by-row가 나빴던 이유는 단순히 느려서가 아니라 **알림 개수만큼 왕복(round-trip)이 생기기 때문** — bulk UPDATE는 왕복을 1회로 줄인다.

### 목록·지도 오버페칭 제거 (컬럼 프로젝션) — N+1과는 다른 축이라는 것
- N+1은 "쿼리 개수"의 문제, 오버페칭은 **쿼리 1개가 몇 개의 쓸모없는 컬럼을 실어 나르는가**의 문제. 둘은 독립적이라 N+1을 없애도 오버페칭은 안 없어진다.
- Board(user 27→3컬럼), Users관리자(27→12컬럼, 쿼리 2→1), Care 지도(14필드 projection, HTTP -58%/-74%).
- 2026-07-10 실측: Board 응답시간 -25%(바이트 불변 — 컬럼을 줄여도 페이지네이션이 같으면 전체 전송량은 그대로일 수 있다는 걸 보여주는 반례), Users 바이트 -33%/시간 -15%, Care 바이트 -58%/시간 -74%.

### Board 인기글 배치 집계 — 왜 순차 3개를 병렬로 바꿨나
- 좋아요/댓글수/조회수 배치조회 3개가 서로 **독립적인 쿼리**인데도 순차 실행(`like(100ms)→comment(100ms)→view(100ms) ≈ 300ms`)되고 있었다. 서로 의존관계가 없다는 게 병렬화의 전제조건이라, `CompletableFuture.supplyAsync` + `allOf`로 동시 실행해 총 대기시간을 이론상 1/3(≈100ms)로 줄였다. 곁들여 `getLikeCountsBatch`가 LIKE/DISLIKE 전체를 반환받아 Java에서 필터링하던 것도 `AND reactionType='LIKE'`로 DB에서 필터링하도록 개선.
- **근거**: `refactoring/board/board-popularity-snapshot-batch-analysis.md` · `refactoring/board/board-popularity-snapshot-batch-refactoring.md`

### 관리자 유저 검색 — QueryDSL 도입, "성능"이 아니라 "동적 쿼리 안티패턴 정리"라는 정직한 포지셔닝
- 기존 코드는 `:param IS NULL OR ...` 패턴이었다. 파라미터가 null이어도 조건이 SQL WHERE절에 그대로 남아, 옵티마이저가 "null이면 전체/아니면 필터"를 하나의 실행계획으로 처리해야 해서 인덱스가 있어도 활용 못 하고 스캔형 계획을 택하기 쉽다.
- **대안 비교**: A(QueryDSL) vs B(Specification 통일, board 도메인과 스타일 일치) vs C(그대로 둠). **코드베이스 순수 관점만 보면 B가 정답**(신규 의존성 0, 기존 스타일 유지)이지만, 이 작업의 실제 목적이 "채용공고가 명시한 QueryDSL 실사용 경험 확보"였기 때문에 **A를 선택**했다. 문서에 이 트레이드오프(일관성 손해 vs 채용 대비)를 그대로 남겨서, "왜 board는 Specification인데 여기는 QueryDSL이냐"는 질문에 답할 수 있게 해뒀다.
- ⚠️ 정직한 전제: 이 쿼리는 `CAST(... AS string)`과 선행 와일드카드 `LIKE %:keyword%` 때문에 QueryDSL로 바꿔도 실행계획이 극적으로 좋아지지 않는다(성능 성과로 과장하지 않음). 진짜 가치는 안티패턴 제거 + 중복 WHERE절 통합 + 이력서 키워드.
- **근거**: `refactoring/querydsl/00-admin-user-search-querydsl-decision.md` · `refactoring/querydsl/01-before-after-sql-evidence.md`

## 9. board 깊은 페이지 페이징 판단 (2026-07-15, `핵심성과_분석.md` 미반영 — 가장 최신 사례이자 "대안 비교" 서술이 가장 잘 된 사례)

### 문제의 두 겹 원인

`OFFSET`은 "건너뛰기"가 아니라 "만들고 버리기"다 — 49,980번째 행을 알려면 앞의 49,980개를 정렬 순서대로 실제로 만들어야 한다. 게다가 필터(`users.is_deleted=0 AND status='ACTIVE'`)가 **조인 건너편**에 있어서, board 인덱스만으로는 어느 행이 페이지에 낄 자격이 있는지 알 수 없고 5만 행×users PK 조회가 강제된다. 실측: OFFSET 0(1.5ms) → OFFSET 10,000(51ms) → OFFSET 49,980(114~147ms). 같은 이유로 자동생성 COUNT도 매 호출 60,001행(users 조인)을 검사한다.

### 왜 이 방식인가 — 검토한 3개 대안과 기각/채택 이유

| 대안 | 성능 | 기각/채택 이유 |
|---|---|---|
| **키셋 페이징** | 최고(O(1)), COUNT도 사라짐 | 앱 전체 페이징이 단일 공유 컴포넌트(`Common/PageNavigation.js`, 12개 화면)에 의존하는데, 이 컴포넌트는 총건수·페이지 점프·맨뒤 버튼을 전제로 함. 키셋은 이 UI에 원리적으로 못 얹혀서, board 하나만 무한스크롤로 빠지면 앱 전체의 페이징 정체성이 board 때문에 쪼개진다 → **기각** |
| **아무것도 안 함** | 그대로 | 비싼 구간(수백~수천 페이지)이 실사용과 안 겹치지만, 공유 컴포넌트의 "맨 뒤" 버튼이 실제로 최대 offset에 도달시킬 수 있는 유일한 트리거였음. 아래 대안이 COUNT까지 함께 고치는 이점이 더 커서 → **기각** |
| **지연 조인 + `author_visible` 비정규화** | 커버링 인덱스 스캔으로 완화 | 번호 UI(공유 컴포넌트)를 그대로 두면서 문제를 풀 수 있고, 비정규화 덕에 COUNT도 board 단일 테이블 카운트가 됨 → **채택** |

**핵심 통찰**: 느림의 근본 원인이 "조인 건너편 필터"이므로, 그 판정(`미탈퇴 AND 미영구정지`)을 board 자체 컬럼으로 내리면 ① 지연 조인 서브쿼리가 커버링 인덱스가 되고 ② 페이지가 결손 없이 채워지고 ③ COUNT가 board 단일 인덱스 카운트가 된다 — **하나의 비정규화로 세 가지 문제가 동시에 풀리는 구조**라는 게 채택 근거다.

### 왜 `author_visible`은 탈퇴+영구정지만 가리고 일시정지(SUSPENDED)는 안 가리는가

제품 결정: `author_visible = (is_deleted=0 AND status<>'BANNED')`. 일시정지는 임시 상태라 계속 노출하고, 탈퇴·영구정지 같은 **영구 상태만** 숨긴다. Care 도메인이 이미 "SUSPENDED는 상태 변경 없이 읽기필터로, BANNED만 행 변경"이라는 철학을 쓰고 있어서 방향을 맞췄다 — **영구 이벤트에만 동기화가 걸리므로 일시정지↔복구 사이의 불필요한 write 증폭이 사라진다**는 부수 효과도 있다.

### 왜 이벤트 리스너가 아니라 DB 트리거로 동기화하는가

회원 상태를 바꾸는 경로가 관리자 API, 제재 서비스, 탈퇴, 로그인 재활성화 등 여러 곳이다. 이벤트 리스너는 경로마다 일일이 배선해야 해서 하나라도 빠뜨리기 쉽지만, **`users AFTER UPDATE` 트리거 하나면 어떤 경로로 상태가 바뀌든 무조건 걸린다.** 이 저장소가 이미 `geo_point` 비정규화에 트리거를 쓰고 있어(V4/V5) 패턴 일관성도 있다.

```sql
CREATE TRIGGER trg_board_author_visible AFTER UPDATE ON users
FOR EACH ROW
  IF (OLD.is_deleted <> NEW.is_deleted)
     OR ((OLD.status = 'BANNED') <> (NEW.status = 'BANNED')) THEN
    UPDATE board SET author_visible = IF(NEW.is_deleted = 0 AND NEW.status <> 'BANNED', 1, 0)
    WHERE user_idx = NEW.idx;
  END IF;
```

`is_deleted`나 BANNED 경계가 실제로 바뀔 때만 발동하도록 조건을 걸어서, 로그인 시 `last_login_at` 갱신 같은 흔한 UPDATE에는 걸리지 않는다. 엔티티 쪽은 `@Column(updatable = false)`로 매핑해 JPA가 UPDATE 시 이 값을 되돌리지 못하게 막았다 — **갱신 소유권을 트리거 하나로 고정**하기 위함.

### 실행 구조 — 2단계 지연 조인

```
1단계 (native, 깊은 skip): SELECT idx FROM board
  WHERE is_deleted=0 AND author_visible=1
  ORDER BY created_at DESC LIMIT :size OFFSET :offset
  → idx_board_visible_created 커버링, users 조인 없음

2단계 (JPQL projection, 20건만): SELECT new BoardListItemDTO(...) FROM Board b JOIN b.user u
  WHERE b.idx IN :ids ORDER BY b.createdAt DESC
  → 살아남은 20개만 작성자 조인 (재필터 불필요)

COUNT (단일 테이블): SELECT COUNT(*) FROM board WHERE is_deleted=0 AND author_visible=1
  → users 조인 사라짐
```

닉네임 검색(`searchBoardListItemsByNickname`)만은 예외로 지연 조인을 적용하지 않았다 — 닉네임 검색은 users 조인이 필수이고 결과 자체가 작아 깊은 offset이 발생하지 않으므로, 굳이 2단계로 쪼갤 이유가 없었다(불필요한 복잡도를 추가하지 않는다는 판단).

### 실측 결과

깊은 페이지 커버링 인덱스 스캔 24~32ms(비교군 66~84ms, 구코드 재현 133ms), COUNT 단일 테이블 7~25ms(구코드 22~32ms). **페이지 결손 검증**: 전체 2,500페이지 중 596페이지(23.8%)에 숨김 대상 글이 유입돼 있었음 — 비정규화가 실제로 필요했다는 직접 증거. k6 30s/20VU 15,555req 100% 200, p95 63.91ms.

### 이 결정이 다른 도메인엔 왜 적용 안 됐는가

지연 조인+비정규화가 이득이 되려면 "큰 테이블(깊은 offset이 실제로 발생) + 조인 건너편 필터"가 함께 있어야 한다. board(5만 행)만 두 조건을 충족한다. missing_pet·meetup·care는 필터는 있지만 끝까지 가도 수천 행이라 몇 ms 차이라 보류. 관리자 목록은 총계·점프가 기능 요구라 그대로 두고, chat은 방별 파티션이라 애초에 깊은 offset이 생기지 않는다. **"어디에나 적용 가능한 만능 해법"이 아니라 조건이 맞는 곳에만 쓴다는 걸 명시한 것 자체가 판단력의 근거.**

### 알려둔 트레이드오프

**키셋 페이징으로 바꾸면 COUNT까지 없앨 수 있지만, 페이지 번호 점프("37페이지로 이동")를 포기해야 해서 성능만으로 결정할 수 없다** — 이게 이 사례에서 가장 강조되는 트레이드오프다.
