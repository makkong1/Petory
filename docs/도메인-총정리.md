## User — 인증·프로필·제재의 허브였다가 leaf로 정리됨

- **책임**: JWT+OAuth2 인증, 프로필/펫 관리, 휴면계정 배치, 소셜 계정 연결, 제재 상태 동기화.
- **핵심 구조**: Access(15분)+Refresh(1일, DB저장) JWT, `JwtAuthenticationFilter`가 매 요청 DB로 권한 재조회. 이메일 인증은 단일 토큰+purpose enum. 휴면계정은 1년 미로그인 배치 전환 + 로그인 시 본인 재활성화.
- **동시성 포인트**: 소셜 로그인 동시 최초가입은 DB Unique 제약(backstop), 경고 횟수는 원자적 UPDATE.
- **최근 구조 변화**: `analysis/domain-dependency-refactoring-2026-07.md` 작업으로 `user`가 care/location/meetup/report를 역참조하던 허브 구조에서 **완전한 leaf**(common·file만 의존)로 정리됨. profile 집계 계층 신설, `ReportActionType`을 common으로 추출.
- **알려진 이슈**: socialUsers Lazy N+1은 `@BatchSize(50)`로 해결(`refactoring/user/social-users-query/`), 로그인/Admin삭제 중복조회도 해결(`refactoring/user/*/sequence-diagram.md`). 제재 우회 6건 중 5건 해결, 1건(관리자 변경 시 UserSanction 이력 통일)은 잔여(`troubleshooting/users/sanction-auth-gap-2026-06-28.md`).
- **근거 문서**: `domains/user.md` · `architecture/user/사용자 인증 및 프로필 아키텍처.md` · `architecture/user/이메일 인증 시스템 아키텍처.md` · `db_concept/db-concept-highlights-user.md` · `interview/concepts/배경/09_보안_JWT_인증.md` · `refactoring/user/*`

## Board — 커뮤니티 게시판

- **책임**: 게시글/댓글/반응(좋아요·싫어요)/조회수/인기글 스냅샷.
- **핵심 알고리즘**: 인기글 점수 = 좋아요×3 + 댓글×2 + 조회수(`자료구조/알고리즘/algorithm/board/`), 4단계 fallback 스냅샷 조회, 배치 집계는 `CompletableFuture` 병렬화.
- **성능 이력 (최신 수치는 `핵심성과_분석.md` §1 기준)**: N+1 301→3쿼리(-99%). 2026-07-13 대량시드 실측에서 목록이 매 페이지 5만행 filesort(선택도 오판)하던 것을 히스토그램으로 해결. 2026-07-15에는 **깊은 페이지(OFFSET 49980) 문제**를 `author_visible` 비정규화 + 2단계 지연조인으로 추가 해결(24~32ms, 페이지 결손 23.8% 검증) — 이건 아직 `핵심성과_분석.md`에 반영 안 된 최신 성과.
- **동시성**: 조회수 `INSERT IGNORE`, 좋아요/댓글수는 원자적 증가.
- **알려진 한계**: 반응 API가 body의 `userId`를 신뢰(권한검증 아님), 상세 캐시(`@Cacheable`)는 조회수 실시간 반영 때문에 의도적으로 비활성. `GET /api/boards/my-posts`도 같은 종류의 문제였음 — 클라이언트가 보낸 `userId`를 신뢰해 남의 글 목록이 조회 가능했고(파라미터 생략 시 400이 아니라 500), 2026-07-14 쿼리 감사에서 발견해 `@AuthenticationPrincipal` 기준으로 수정(2026-04-14에 Chat/Care를 같은 이유로 고쳤을 때는 놓쳤던 곳).
- **근거 문서**: `domains/board.md` · `architecture/board/커뮤니티 게시판 아키텍처.md` · `db_concept/db-concept-highlights-board.md` · `analysis/board-deep-page-2026-07.md` · `analysis/entity-schema/evidence/query-baseline-2026-07-13.md` · `refactoring/board/*` (특히 `evidence/n-plus-one-reverify-2026-07-12.md`)

## Care — 펫케어 요청·매칭

- **책임**: 케어 요청 생성/지원/채팅 거래확정/완료·취소, 리뷰.
- **핵심 흐름**(2026-08-08 재설계): 요청 등록 시 **에스크로 HOLD**(상대 미정) → 채팅 거래확정 시 지급대상 배정 → **양쪽이 이행 완료 확인**해야 지급 / 취소·만료·삭제 시 환불. 상태전이 OPEN→IN_PROGRESS→COMPLETED/CANCELLED (`transitionTo`에 허용 전이 가드, 종착 상태 되돌리기 불가).
- **동시성**: 거래 양측 동시확정 시 격리수준 탓 로직이 둘 다 skip되는 stuck state를 발견 → Conversation 비관적 락으로 해결(`troubleshooting/care/care-deal-confirmation-race-condition.md`).
- **성능**: N+1 151→4쿼리(-97.4%, `핵심성과_분석.md` §1 최신 재검증치). `file` 테이블에 인덱스가 없어 첨부 조회가 풀스캔이던 것도 재검증 중 발견해 5~14배 개선.
- **쿼리 감사에서 발견된 이슈(2026-07-14)**: 검색 엔드포인트가 FULLTEXT 인덱스 없이 `MATCH()`를 써서 **항상 HTTP 500**(공개+관리자 양쪽) → 인덱스 추가로 해결. 목록/주변검색은 인덱스 3개뿐(전부 PK/FK)이라 풀스캔이었고, 주변검색 선택도 208배 오판 → SPATIAL 인덱스 추가로 3,000행 풀스캔→208행.
- **2026-08-08 정합성 수정 6건**: 스케줄러가 예정일 경과만으로 자동 지급하던 것, 제공자 단독 완료로 돈을 가져갈 수 있던 것, 리뷰 작성자를 요청 본문에서 받던 보안 구멍, 상태 전이·수정·삭제 가드 부재. 각 수정은 되돌려 RED 확인. → `refactoring/care/care-settlement-integrity-2026-08-08.md`
- **알려진 한계**: 확정 후 일방 취소(요청자가 취소하면 제공자가 일하고 못 받음) — 분쟁 처리가 필요해 의도적으로 남김. ~~에스크로 실패 시 케어 트랜잭션이 롤백되지 않음~~은 **오서술이었다**(항상 롤백됐다).
- **근거 문서**: `domains/care.md` · `architecture/care/*` · `db_concept/db-concept-highlights-care.md` · `analysis/query-audit/care-2026-07-14.md` · `refactoring/care/*`

## Payment — 펫코인·에스크로

- **책임**: 펫코인 잔액 관리(PG 미연동, 내부화폐 시뮬레이션), 에스크로 HOLD/RELEASED/REFUNDED.
- **동시성**: `findByIdForUpdate` 비관적 락으로 Lost Update 방지(동시 충전 5건 기대150 실제110 재현 후 해결, `refactoring/payment/petcoin-service-race-condition.md`). 락 순서(escrow→users)까지 문서화됨.
- **트랜잭션 경계 개선**: 통계 기록(`recordPayment`)이 코인 지급(`releaseToProvider`)과 같은 트랜잭션에 있어 통계 실패가 코인 지급까지 롤백시키던 잠재 버그를, `PaymentRecordedEvent` + `AFTER_COMMIT` 이벤트로 분리해 제거(`핵심성과_분석.md` §6).
- **알려진 한계**: 충전(`POST /api/payment/charge`)에 멱등키가 없어 재시도로 두 번 반영된다(PG 미연동이라 실질 피해는 없음). ~~에스크로 실패가 Care 쪽으로 롤백 전파 안 됨~~은 **오서술이었다** — `REQUIRED` 합류라 항상 전파됐고, 2026-08-08에 삼키던 `try/catch`를 제거해 원인 예외까지 전달되게 고쳤다.
- **근거 문서**: `domains/payment.md` · `architecture/payment/펫코인 결제 아키텍처.md` · `자료구조/알고리즘/algorithm/payment/펫코인-알고리즘.md` · `troubleshooting/payment/*` · `refactoring/payment/*`

## Chat — 1:1/그룹 채팅

- **책임**: WebSocket(STOMP) 기반 실시간 채팅, 케어 매칭 시 1:1방·모임 생성 시 그룹방 자동 생성.
- **성능**: N+1 최신 재검증치 41→4쿼리(-90.2%, 참여자 조회 1회 누락분까지 포함해 이전 21→4보다 실제로 더 큰 개선 — `핵심성과_분석.md` §1의 정정 사례). 읽음처리(markAsRead)는 전체조회 로직 제거로 트랜잭션 범위 축소.
- **동시성**: unreadCount 원자적 증가. `REQUIRES_NEW` self-invocation 문제(같은 클래스 내 호출 시 프록시 미적용)를 별도 Service 분리로 해결.
- **알려진 한계**: `CARE_APPLICATION` confirmDeal 관련 로직 미완성 부분 존재, 제재 사용자 채팅은 안내 플래그만 있고 메시지 마스킹은 없음.
- **근거 문서**: `domains/chat.md` · `architecture/chat/채팅 시스템 설계.md` · `db_concept/db-concept-highlights-chat.md` · `refactoring/chat/*` (특히 `evidence/n-plus-one-reverify-2026-07-12.md`)

## Location — 위치기반 서비스

- **책임**: 주변 병원·카페 등 반경 검색, 리뷰, 공공데이터 CSV 배치 임포트.
- **핵심 알고리즘**: `ST_Within`(POLYGON, SRID 4326) + `ST_Distance_Sphere` 2단계 공간쿼리, lat/lng 있으면 위치 우선 분기, `size=300` 고정, 지역계층검색(도로명→읍면동→시군구→시도)은 현재 비활성.
- **성능**: 초기 로드 무제한 전체조회(22,699건)→10km 반경검색+`DEFAULT_RADIUS_LIMIT=100`으로 전환, 2026-07-12 재검증에서 22.4MB/531.8ms→100KB/50.9ms(바이트 -99.6%/시간 -90%) 확인. 시군구 WHERE 검색이 공간쿼리보다 5-6배 빠르다는 별도 실측도 있음(`troubleshooting/location/search-strategy-comparison.md`).
- **인덱스 성숙도**: 쿼리 감사(2026-07-14)에서 **인덱스 9개로 12개 도메인 중 가장 모범적**이라고 판정됨(care의 3개와 대조).
- **알려진 한계**: 반경검색이 POLYGON bbox 근사라 극단적 위치에서 이론적 오차 가능(모니터링 대기), 지도 UX(즉시 API 호출, 마커 500개)는 여전히 개선 여지 있음.
- **근거 문서**: `domains/location.md` · `architecture/location/*` · `db_concept/db-concept-highlights-location.md` · `refactoring/location/*` (archive/ 5건은 과거 리팩토링, 최신은 `주변서비스-현행vs설계안-비교.md`)

## Meetup — 오프라인 모임

- **책임**: 모임 생성/참여/그룹채팅 자동 생성.
- **동시성**: 참가 인원 초과를 **원자적 조건부 UPDATE**(`WHERE currentParticipants < maxParticipants`)로 구조적 차단(`핵심성과_분석.md` §2). 저경합에선 비관적 락이 더 빠르다는 걸 실측했지만, 락/데드락 관리 부담 제거를 위해 원자적 UPDATE를 선택했다는 근거까지 남김.
- **성능 세대**: 근처 모임 조회는 Gen1(전체 메모리 로드→Java Haversine) → Gen2(Bounding Box DB필터, 486→273ms, 스캔 -96%) → **현재 Gen3(공간 인덱스 `ST_Within`+`ST_Distance_Sphere`, `findNearbyMeetupIds`)**로 재구현됨. 면접 등에서 세대를 명시해야 함(`analysis/리팩토링-순서-2026-07.md` §3).
- **채팅방 생성 안전망**: `afterCommit()` 이벤트로 분리 + 재시도 + 복구 스케줄러 3단계.
- **쿼리 감사 발견**: 검색/주변 엔드포인트에 페이징이 없어 500건씩 무제한 반환되던 문제(N+1처럼 보였지만 `@BatchSize` 정상 동작이었음) → 페이징 추가로 583ms→43ms.
- **근거 문서**: `domains/meetup.md` · `architecture/meetup/산책 & 오프라인 모임 아키텍처.md` · `db_concept/db-concept-highlights-meetup.md` · `analysis/query-audit/meetup-2026-07-14.md` · `refactoring/meetup/*`(nearby-meetups/, participants-query/, subquery-optimization/ 3개 실험 폴더)

## Notification — 알림

- **책임**: MySQL 영구저장 + Redis(최신 50개, TTL 24h) 캐시 + SSE(앱 열림) + FCM(앱 꺼짐) 4단 전달.
- **성능**: 전체읽음 처리가 알림 100개당 102개 statement 발생하던 것을 JPQL bulk UPDATE 1개로 전환(-99%, `refactoring/notification/notification-read-performance-optimization.md`).
- **알려진 한계**: DB저장과 Redis/SSE/FCM 발송이 outbox 없이 같은 메서드 안에서 호출돼 비원자적(하나 실패해도 나머지가 그대로 진행될 수 있음). 서버 메모리 기반 SSE라 스케일아웃 시 Redis Pub/Sub 등이 필요.
- **근거 문서**: `domains/notification.md` · `architecture/notification/알림 시스템 아키텍처.md`(구조 요약) / `architecture/user/알림 시스템 아키텍처.md`(코드 상세) · `자료구조/알고리즘/algorithm/notification/`

## Statistics — 일/주/월 통계

- **책임**: 실시간 쿼리 대신 매일 18:30 배치로 Daily/Weekly/Monthly 집계(Daily Summary Pattern), 결제는 예외적으로 이벤트 즉시반영.
- **최근 변화**: DAU 계산을 `lastLoginAt` 기반(부정확)에서 `login_events` 테이블 기반 `DISTINCT` 집계로 전환(2026-06-28), Critical 버그 4건(DAU 원천오류, 결제-배치 충돌로 지표 영구 0, self-invocation, race) 전부 수정완료.
- **쿼리 감사 결과**: 12개 도메인 중 **최대 검사 1행으로 가장 깨끗한 도메인**으로 판정.
- **근거 문서**: `domains/statistics.md` · `architecture/관리자 대시보드 & 통계 시스템 아키텍처.md` · `자료구조/알고리즘/algorithm/statistics/` · `refactoring/statistics/*`

## Recommendation — 반려생활 추천 (NLP 연동)

- **책임**: 위치검색/커뮤니티/케어 활동 이벤트 → Python FastAPI NLP 서버 의도분석 → signal 저장 → 추천카드.
- **핵심 설계**: 무거운 NLP를 요청 경로 밖(`AFTER_COMMIT` 이벤트 + 전용 스레드풀 core2/max6/queue500)으로 분리, NLP 호출 timeout 3초 격리 + 실패 시 fail-closed, Redis TTL dedup으로 중복분석 방지. 스코어링은 거리0.35/평점0.30/리뷰수0.20/인기도0.10/태그매칭0.05 가중합.
- **진화 과정**: 초기 하드코딩 룰 기반 → 트래픽 정책(bounded executor) 도입 → 2차 리뷰(R1~R9, 7건 완료) → petType enum 계약 불일치(Java/Python) 발견·수정 → AI/LLM 전환 검토(설계 단계, 미착수) → signal이 저장돼도 사용자에게 전달 안 되는 gap 발견(MEDICAL+HIGH는 SSE 알림 MVP 제안, 구현 대기).
- **근거 문서**: `domains/recommendation.md` · `architecture/recommendation/반려생활 추천 & NLP 아키텍처.md` · `refactoring/petRecommendation/*`(시간순 6개 문서) · `troubleshooting/petRecommendation/*`

## File — 첨부파일

- **책임**: 로컬 파일시스템 저장 + `FileTargetType` 폴리모픽 첨부 연결, 도메인별 `syncSingleAttachment`.
- **성능**: 배치 조회로 N+1 완화(care/missing-pet 재검증 과정에서 `file` 인덱스 부재도 함께 발견·해결).
- **알려진 한계**: 관리자 삭제는 DB row만 삭제하고 물리 파일은 삭제되지 않음.
- **근거 문서**: `domains/file.md` · `architecture/file/첨부파일 저장 & 연결 아키텍처.md`

## Activity — 활동 타임라인

- **책임**: 전용 테이블 없이 Care/Board/MissingPet을 조회 시점에 합성하는 read model.
- **알려진 한계**: 메모리 정렬/페이징(확장성 낮음), 리뷰 데이터는 수집 안 됨. `GET /api/activities/my`는 `@PreAuthorize`조차 없이 `SecurityConfig`의 `/api/**` catch-all에만 기대고 있어, 로그인한 누구나 `userId` 파라미터만 바꾸면 남의 활동 내역(게시글·케어요청·댓글)을 전부 읽을 수 있었음(2026-07-14 쿼리 감사에서 발견, `@AuthenticationPrincipal` 기준으로 수정) — Board와 같은 시기·같은 종류의 발견.
- **근거 문서**: `domains/activity.md` · `architecture/activity/사용자 활동 타임라인 아키텍처.md`

## Admin — 관리자

- **책임**: 도메인별 CRUD·통계 대시보드·감사 로그, `/api/admin`·`/api/master` 권한 경계.
- **구조적 특징**: Facade+감사로그 경로와 도메인 서비스 직접호출(감사로그 없음) 경로가 공존 — 2026-04-18 Facade 레이어 도입 이후에도 완전 통일은 안 됨.
- **쿼리 감사 결과**: 프로젝트에서 **유일하게 확인된 진짜 N+1**이 여기서 나옴(`/api/admin/care-requests` 20건→60쿼리, fetch join 누락) → 처방 후 7쿼리로 해결. 사용자 목록도 `created_at` 인덱스 없이 풀스캔+filesort였음.
- **근거 문서**: `domains/admin.md` · `architecture/admin/관리자 운영 아키텍처.md` · `analysis/query-audit/admin-2026-07-14.md` · `refactoring/admin/*`
