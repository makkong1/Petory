## 어디서 시작했나

포트폴리오에 쓸 에스크로 사례를 정리하려고 코드를 열었다가, **"멱등키가 없다"고 적어둔 문장이 사실과 다르다**는 걸 발견한 데서 시작했다. 돈이 움직이는 진입점 4개를 실제로 확인하니 결과가 갈렸다.

| 진입점 | 같은 요청이 두 번 오면 |
|---|---|
| 코인 충전 `POST /api/payment/charge` | 🔴 두 번 반영. 막는 장치 없음 |
| 거래 확정 → 차감 | 🟡 UNIQUE 위반으로 차감까지 함께 롤백 |
| 완료·취소 → 지급/환불 | 🟡 상태 가드에 막혀 두 번째는 진입 불가 |

즉 **돈이 새는 건 충전 하나뿐**이고, 나머지는 "돈은 안전하지만 멱등하지는 않다"(재시도가 원래 결과 대신 에러를 받는다)가 정확한 서술이다. 멱등의 핵심은 중복 차단이 아니라 **같은 요청에 같은 응답을 주는 것**인데, HTTP 계층에 요청 식별자가 없어 앱이 재시도와 신규 요청을 구분할 방법 자체가 없다.

이 표를 만드는 과정에서 더 큰 문제들이 나왔다.

## Phase 0 — 재설계와 무관하게 이미 틀린 것 (4건)

### 1. 거래 확정이 에스크로 실패를 삼키고 있었다 (`2c904ad3`)

**문제.** `ConversationService.confirmCareDeal`이 에스크로 생성 실패를 `try/catch`로 잡고 *"코인 차감 실패 시 거래 확정은 진행하되, 로그만 남김"*이라는 주석까지 달아두었다.

**원인.** 그 동작은 **애초에 불가능했다.** `createEscrow`가 `REQUIRED`로 같은 트랜잭션에 합류하므로 실패가 트랜잭션을 rollback-only로 표시한다. 예외를 삼켜도 바깥 커밋에서 터지며 전부 롤백된다.

**해결.** 예외를 그대로 전파한다. 전파로 바꾼 실효는 롤백을 만드는 게 아니라 **원인을 남기는 것**이다.

| | 옛 코드 | 지금 |
|---|---|---|
| DB 상태 | 롤백 | 롤백 *(동일)* |
| 던져지는 예외 | `UnexpectedRollbackException` | 원인 예외 |
| HTTP 응답 | **500** 알 수 없는 오류 | **400** 원인 명시 |

> **배운 것**: 예외를 잡는 것만으로 격리했다고 착각하게 되는 자리가 트랜잭션 전파다.
> **테스트 설계**: 상태는 전후가 같으므로 상태를 단언하면 옛 코드에서도 통과하는 눈먼 테스트가 된다. **호출자가 받는 예외**를 단언한다.

### 2. 리뷰를 남의 이름으로 쓸 수 있었다 (`ef58f978`)

**문제.** `POST /api/care-reviews`가 `reviewerId`를 **request body**에서 받았다. `@PreAuthorize("isAuthenticated()")` 뿐이라 인증만 된 사용자면 누구나 요청자인 척 본문을 꾸며 리뷰를 쓸 수 있었다. 리뷰는 평점·프로필에 반영되므로 실질 피해가 있다.

**해결.** `AuthenticatedUserIdResolver`로 교체. 중복 확인·작성자 검증·reviewer 조회 세 곳 모두 인증 주체 기준으로 바꿨다.

### 3. 스케줄러가 예정일 경과만으로 돈을 지급했다 (`d00f6919`)

**문제.** `CareRequestScheduler`가 **매시간** 예정일 지난 `OPEN`/`IN_PROGRESS`를 `COMPLETED`로 바꿨고, `updateStatus`가 `COMPLETED`에서 에스크로를 제공자에게 지급한다.

> **아무도 완료를 누르지 않아도 예정일만 지나면 돈이 넘어갔다.** 실제 이행 여부와 무관하게.

**해결.** 이행 여부는 당사자만 알 수 있으므로 `IN_PROGRESS`는 건드리지 않고 경고만 남긴다. 성사되지 않은 `OPEN`은 `CANCELLED`로 정리한다(신청자도 없던 글이 "완료"일 수는 없다).

### 4. 상태 전이 가드가 없었다 (`d00f6919`)

**문제.** `transitionTo`가 검사 없이 대입해 `COMPLETED → CANCELLED`가 통했다. 그때 에스크로는 이미 `RELEASED`라 환불 분기가 스킵되고 로그만 남는다 → **상태는 취소인데 돈은 제공자에게 가 있는** 불일치.

**해결.** `CareRequestStatus.canTransitionTo()`로 허용 전이를 못박고 `COMPLETED`/`CANCELLED`를 종착으로 뒀다. **같은 상태로의 재요청은 no-op**으로 남긴다 — 재시도가 에러가 되면 안 된다.

```
OPEN        → IN_PROGRESS | CANCELLED
IN_PROGRESS → COMPLETED   | CANCELLED
COMPLETED   → (없음)
CANCELLED   → (없음)
```

### 5. 끝난 거래의 조건이 사후에 바뀌었다 (`e6628c68`)

**문제.** `updateCareRequest`에 작성자 확인만 있고 상태 가드가 없어, 이미 `COMPLETED`된 케어의 날짜·장소·펫을 바꿀 수 있었다.

**해결.** `OPEN`일 때만 수정 허용. **관리자도 예외가 아니다** — 관리자가 우회할 수 있으면 가드가 아니다.

## Phase 1 — 완료를 양쪽 합의로 (`f0a2b91a`, `V13`)

**문제.** `updateStatus`는 요청자 **또는** 승인된 제공자 아무나 호출할 수 있었고, `COMPLETED`가 되는 순간 정산됐다.

> **제공자가 혼자 완료를 눌러 요청자 동의 없이 돈을 가져갈 수 있었다.**

프론트도 이 구멍과 짝을 이뤘다 — 완료 버튼이 `isProvider`일 때만 렌더링되고, 그 한 번의 클릭이 곧 정산이었다.

**해결.**

- `POST /api/care-requests/{id}/complete` 신설. 요청자·제공자가 각자 호출하고 **양쪽이 모두 확인해야** `COMPLETED` + 정산
- `updateStatus`의 `COMPLETED`는 **관리자 전용**(분쟁 조정). 두 경로가 다 열려 있으면 새 가드가 그대로 우회된다
- 프론트: 버튼을 양쪽에 노출하고, 이미 확인한 쪽은 "⏳ 상대방 확인 대기 중"으로 비활성화

**설계 판단.**

| 결정 | 근거 |
|---|---|
| 비관적 락 (`CareRequest` 행) | 양쪽이 동시에 누르면 둘 다 "상대도 확인했나"를 읽고 각자 정산으로 넘어갈 수 있다. 읽고 판단해서 쓰는 구간이라 원자적 UPDATE로 대체되지 않는다 |
| `boolean` 아닌 `datetime` 2개 | `NULL` = 미확인이라 담는 정보는 같은데, 분쟁 시 "언제 확인했는가"가 남는다 |
| 같은 쪽 재확인은 시각 미갱신 | 재시도 안전 |
| 기존 `COMPLETED` 데이터 미소급 | 실제로 양쪽이 확인한 적이 없다. 완료 여부의 정본은 계속 `status` |

## Phase 2 — 정산 시점 이동 (`1a137c51`, `V14`·`V15`)

### 왜 옮겼나

`createCareRequest`에는 **이미 잔액 확인이 있었다.**

```java
if (user.getPetCoinBalance() < dto.getOfferedCoins()) {
    throw CareValidationException.insufficientBalance();
}
```

등록 시점에 지급 능력을 보겠다는 의도는 처음부터 있었던 셈인데, **확인만 하고 잡지는 않으니 TOCTOU**였다. 확인과 실제 차감(거래 확정) 사이에 잔액을 다른 데 쓰면 확정 순간에 깨졌고, 제공자는 신청하고 채팅까지 마친 뒤에야 그 사실을 알았다.

> **충전형 코인이라 가능한 선택이다.** 등록 시 차감은 새로 결제를 받는 게 아니라 플랫폼 안에서 잔액 → 에스크로로 옮기는 것뿐이다. 외부 결제(카드·계좌)라면 등록 시 결제창을 띄우는 셈이라 이탈이 크지만, 사용자가 이미 충전해둔 내부 화폐에는 그 비용이 없다.

### 무엇을 바꿨나

| 지점 | Before | After |
|---|---|---|
| 등록 | 잔액 **확인**만 | **차감 + `HOLD`** (`provider_idx` NULL = 상대 미정) |
| 확정 | `createEscrow`(차감+생성) | `assignProvider`(지급 대상 배정만) |
| 금액 수정 | 불가(무시됨) | `OPEN`에서 허용 + **차액 정산** |
| 삭제 | 상태 무관 softDelete | `OPEN`에서만 + **환불** |
| 최소 금액 | `@Min(1)` | `@Min(100)` |

`provider_idx IS NULL`이 "아직 상대가 정해지지 않은 보관"이라는 뜻이 되어, **확정 여부를 판별하는 신호로도 쓰인다**(컬럼 하나가 두 몫).

### 차액 정산이 멱등한 이유

목표 금액을 받는다(증분이 아니라).

```
목표 금액 방식:  수정(금액=8000)   ← 두 번 와도 두 번째는 차액 0
증분 방식:      수정(금액 +3000)  ← 두 번 오면 11,000. 깨짐
```

**멱등키가 필요한 곳과 필요 없는 곳이 같은 도메인 안에 있다.** 차이는 증분이냐 절대값이냐다. 충전은 증분이라 멱등키 없이는 못 막고, 금액 수정은 절대값이라 API 설계만으로 풀린다.

### 금액 합의 — 두 장치가 각각 다른 것을 막는다

확정은 양쪽이 따로 누르고 금액은 `OPEN` 동안 바뀔 수 있다. 아무 장치가 없으면:

```
제공자: 5,000 보고 확정
요청자: 금액을 1,000 으로 수정
요청자: 1,000 보고 확정  → 계약 성립
        ㄴ 제공자의 동의는 5,000 에 대한 것이었다
```

| 장치 | 막는 것 |
|---|---|
| `expectedAmount` (확정 요청 파라미터) | **지금 내가** 화면에서 보고 동의하는 값이 실제와 같은가 → 다르면 409 |
| `confirmedOfferedCoins` (참여자 컬럼) | **이미 있는 동의**가 현재 금액과 같은 금액에 대한 것인가 → 다르면 무효화 |

하나만으로는 위 시나리오가 막히지 않는다. 지키려는 불변식은 **"성립한 계약의 모든 동의는 같은 금액에 대한 것"**이다.

### V15는 V14를 정정한다 — 실패한 첫 시도

V14에서는 **시각 비교**로 낡은 동의를 가려내려 했다. `carerequest.offered_coins_updated_at`(금액 변경 시각)과 `conversationparticipant.deal_confirmed_at`(확정 시각)을 비교하는 방식이다.

**동작하지 않았다.** 두 컬럼 모두 `datetime`(초 단위)이라 **확정과 금액 변경이 같은 초 안에 일어나면 두 시각이 같아져** `isBefore` 비교가 `false`가 된다. `CareDealAmountAgreementTest`의 "금액 변경시 옛 확정 무효화"가 그래서 처음에 실패했다.

`datetime(6)`으로 정밀도를 올려 막을 수도 있었지만, 그건 **"시계가 충분히 촘촘하면 맞는"** 방식이다. 시각 비교 자체를 버리고 **동의한 금액을 직접 기록**하는 방식으로 바꿨다 — 시계와 무관하게 성립한다.

> V14는 이미 두 DB에 적용된 뒤라 파일을 고칠 수 없었다(Flyway 체크섬). 그래서 V15가 정정을 담고, 왜 바꾸는지를 마이그레이션 주석에 남겼다. `offered_coins_updated_at`은 판정 근거로는 쓰지 않지만 "금액이 언제 바뀌었는지"는 화면에 보여줄 수 있어 남겼다.

### 도메인 참조 방향을 지킨 방법

확정 무효화는 **chat 쪽에서** 한다. `dealConfirmed`는 `ConversationParticipant`(chat)에 있고 현재 참조는 `chat → care` 단방향이다. care가 participant를 건드리면 **순환이 생긴다.**

care는 금액만 노출하고, 판단과 무효화는 chat이 한다.

## 검증 방식

**각 수정은 되돌려서 RED를 먼저 확인했다.** 관측된 실패:

| 수정 | 옛 코드에서 실제로 나온 것 |
|---|---|
| try/catch 제거 | `UnexpectedRollbackException: Transaction silently rolled back...` |
| 리뷰 작성자 | 실패 메시지에 옛 코드가 **본문 값 `1L`로 조회**하는 것이 그대로 |
| 상태 전이 가드 | `COMPLETED→CANCELLED` 등 **3건이 예외 없이 통과** |
| 스케줄러 | `expected: IN_PROGRESS but was: COMPLETED` (에스크로도 지급됨) |
| 수정 상태 가드 | 완료·진행 중 케어의 제목이 **그대로 변경됨** |
| 제공자 단독 완료 | `Expecting code to raise a throwable.` (예외 없이 통과) |
| 확정 로직 (Phase 3) | 확정 처리를 옛 코드처럼 로그만 남기게 되돌리면 **3건 전부 실패** |

**RED를 얹을 수 없는 것은 그렇다고 명시한다.** 양방향 완료 확인 6개 중 5개(단독 미정산·양쪽 정산·재확인 멱등·제3자 차단·동시 확인 이중지급 없음)는 새 경로라 옛 코드에 테스트를 얹을 수 없다.

**기존 테스트 2개를 고쳤고, 왜 고쳤는지 주석으로 남겼다.**

- `CareRequestServiceTest.정상_상태변경_COMPLETED`가 `OPEN → COMPLETED`를 "정상"으로 고정하고 있었다 → 관리자 분쟁 조정 경로 테스트로 전환(나중에 이 예외를 "버그"로 보고 지우는 것을 막는 용도)
- `CareDealEscrowFailureTest`는 전제 자체가 바뀌었다(확정에서 잔액 부족이 날 수 없다) → 에스크로가 없는 요청의 확정으로 재현 대상 교체
- Phase 3에서 기존 확정 테스트 3개가 `CARE_REQUEST` 방을 쓰고 있어 지원 단위 fixture로 교체했다

## Phase 3 — 확정 로직이 실행되지 않고 있었다 (`93722fbe`)

**문제.** 문서를 고치다 `docs/domains/care.md`에 있던 경고가 사실임을 확인했다.

한 요청에는 제공자가 여러 명 지원할 수 있으므로 1:1 채팅방은 **지원 단위**여야 한다. 실제로
`createCareRequestConversation`이 만드는 방은 전부 `RelatedType.CARE_APPLICATION`이고
`relatedIdx`는 `careApplicationIdx`다.

그런데 `confirmCareDeal`의 확정 로직은 `CARE_REQUEST`(요청 단위 방)를 전제로 쓰여 있었다 —
방 참여자에서 제공자를 역추론하고, 지원이 없으면 새로 만드는 구조다. 그 분기는 실제로 생성되는
방의 타입과 달라 **한 번도 실행되지 않았고**, `CARE_APPLICATION` 분기는 로그 한 줄이 전부였다.

> **양쪽이 확정 버튼을 눌러도 참여자 플래그만 켜지고 요청 상태·지원 상태·에스크로는 그대로였다.**
> 프론트는 "✓ 양쪽 모두 거래 확정 완료" 배너를 띄우는데 도메인은 멈춰 있었다.

**해결.** `relatedIdx`로 지원을 직접 찾는다. `provider`도 거기 있어 역추론과 조건부 생성이 통째로
사라졌다(15줄 → 5줄). 죽은 `CARE_REQUEST` 분기를 제거해 "요청 단위 방"이라는 옛 가정을 코드에서 지웠다.

확정 시:
- 해당 지원 `ACCEPTED`
- **같은 요청의 나머지 `PENDING` 지원 `REJECTED`** — 그대로 두면 그 지원자들은 계속 대기 중인 줄 안다.
  `CareApplication.reject()`는 메서드만 있고 호출하는 곳이 없어 `REJECTED`가 되는 경로가 아예 없었다
- `CareRequest` → `IN_PROGRESS`
- 에스크로에 지급 대상 배정

이미 확정된 요청의 다른 방에서 확정하면 **이유를 알려주고 거절**한다. 조용히 넘어가면 사용자는
확정된 줄 알고 기다린다.

**곁가지 정정.** Phase 2에서 넣은 금액 대조 코드가 `relatedIdx`를 `careRequestIdx`로 알고 조회하고
있었다. `CARE_REQUEST` 분기 안에 있어 실행되지 않던 코드라 드러나지 않았을 뿐이고, 지원 단위로
정리하면서 같이 바로잡았다.

> **여기서 배운 것.** Phase 1·2에서 만든 것들이 전부 테스트에서만 돌고 있었다. 테스트가 초록불이어도
> **실제 진입 경로가 그 코드에 닿는지는 별개 문제**다. 문서를 고치다 발견했다는 점도 기록해 둔다 —
> 코드만 보고 있었으면 계속 못 봤을 것이다.

## 남긴 것 (의도적)

| 항목 | 이유 |
|---|---|
| **확정 후 일방 취소** | 요청자가 `IN_PROGRESS`에서 취소하면 환불받고 제공자는 일하고 못 받는다. 제대로 풀려면 분쟁 처리가 필요하다 |
| **충전 멱등키** | 재시도로 두 번 충전된다. 현재 PG 미연동 시뮬레이션이라 실질 피해는 없다 |
| **이행 전 `OPEN` 요청** | 에스크로 없이 남는다. 그 시점에 실제로 잡힌 코인이 없어 소급 생성하지 않는다. 확정 시 예외로 드러나며 `CareDealEscrowFailureTest`가 그 경로를 고정한다 |
