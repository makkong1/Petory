# 쿼리 계획 감시의 일반화 — 설계 분석

> **구현 전 분석 문서다.** 결론은 "지금 추상화하지 말고, 먼저 세어보자" 이다.
> 전제가 되는 실측: [query-baseline-2026-07-13.md](./entity-schema/evidence/query-baseline-2026-07-13.md)

---

## 0. 배경

게시글 목록 쿼리가 옵티마이저의 선택도 오판 때문에 매 페이지마다 전체 정렬을 하던 문제를
`BoardListQueryPlanMaintainer` 로 고쳤다(0.17s → 0.00s). 히스토그램을 갱신하고,
`EXPLAIN` 으로 계획이 실제로 좋아졌는지 검증하고, 회귀 시 알람을 울린다.

**문제는 이게 board 목록 쿼리 하나에만 하드코딩되어 있다는 것이다.**
프로젝트 전체의 쿼리는 아직 손도 대지 않았다.

---

## 1. 먼저: 이 문제는 데이터가 늘면 어떻게 악화되나

"선형으로 증가하나?" 에 대한 답 — **선형보다 나쁘다. 계단이 있다.**

| | 비용 증가 |
|---|---|
| **좋은 계획** (현재) | **거의 상수.** 인덱스를 순서대로 20행 읽고 종료. 게시글이 100만 건이 돼도 20행만 읽는다 |
| **나쁜 계획** (수정 전) | 임시테이블에 N행 적재 + N log N 정렬 → **데이터에 비례해 증가** |

### 그리고 이미 절벽을 넘어 있었다

```
tmp_table_size      = 16MB
max_heap_table_size = 16MB

목록 쿼리 1회 실행 → Created_tmp_disk_tables: 493 → 494   (+1)
```

**임시테이블이 메모리 한도(16MB)를 넘겨 디스크에 기록되고 있었다.**
게시글 50,000행 × `content`(LONGTEXT) 가 16MB 를 초과하기 때문이다.
즉 게시판 첫 화면을 열 때마다 디스크 I/O 가 발생했다.

> **정확한 표현**: 데이터에 비례해 증가하다가, **임계점(`tmp_table_size`)에서 디스크로 넘어가며 계단식으로 급증**한다.
> 단순한 선형 증가가 아니라 **계단이 있는 증가**다.

---

## 2. 현재 구현의 한계 — 두 가지, 그리고 하나는 더 심각하다

### 2.1 하드코딩 (지적받은 문제)

`BoardListQueryPlanMaintainer` 는 board 목록 쿼리 전용이다. 감시할 쿼리가 늘어나면
클래스를 복붙하게 된다.

> **용어 정정**: "다형성이 부서졌다"는 정확한 표현이 아니다. 다형성(polymorphism)은
> *같은 인터페이스로 여러 구현을 갈아끼우는 것*이고, 이 클래스는 애초에 인터페이스가 없다.
> **"다형성이 깨진" 게 아니라 "처음부터 일반화되지 않은"** 것이다.
> 정확히는 **하드코딩 / 확장성 부재**다. 지적의 본질은 맞다.

### 2.2 🔴 더 심각한 문제 — 체크 쿼리가 리포지토리와 갈라진다

`BoardListQueryPlanMaintainer` 안에는 **SQL 문자열이 복사되어 있다.**
`SpringDataJpaBoardRepository` 의 JPQL 이 바뀌면?

**체크는 낡은 쿼리를 검사하면서 조용히 초록불을 켠다.**

**이것은 2026-07-13 오전에 잡은 "스키마 사본 4개" 문제와 정확히 같은 종류다.**
사본을 손으로 관리하면 갈라진다. 같은 함정을 다시 판 셈이다.

**추상화보다 이쪽이 먼저 풀어야 할 문제일 수 있다.**

---

## 3. 지금 추상화하면 안 되는 이유

**발견한 문제가 1건이다.** N=1 에서 추상화하면 board 하나에 맞춘 껍데기가 나온다.

다른 쿼리들은:
- 히스토그램이 아니라 **인덱스**가 필요할 수도 있고
- **쿼리 재작성**이 필요할 수도 있고
- 애초에 문제가 아닐 수도 있다 (관리자 통계 쿼리의 풀스캔은 정상이다)

**어떤 모양의 추상화가 맞는지 알 방법이 지금은 없다.**

> **순서를 뒤집어야 한다: 추상화를 먼저 하지 말고, 먼저 센다.**

---

## 4. 세는 방법은 이미 있다 — `performance_schema`

MySQL 이 **모든 쿼리를 이미 기록하고 있다.** 하드코딩할 필요가 없다.

```sql
SELECT LEFT(DIGEST_TEXT, 55)                                AS 쿼리,
       COUNT_STAR                                           AS 실행횟수,
       SUM_ROWS_SENT                                        AS 반환행,
       SUM_ROWS_EXAMINED                                    AS 검사행,
       ROUND(SUM_ROWS_EXAMINED / GREATEST(SUM_ROWS_SENT,1)) AS 배율,
       SUM_CREATED_TMP_DISK_TABLES                          AS 디스크임시,
       SUM_SORT_SCAN                                        AS 정렬스캔,
       SUM_NO_INDEX_USED                                    AS 인덱스미사용
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'petory' AND DIGEST_TEXT LIKE 'SELECT%'
ORDER BY SUM_ROWS_EXAMINED DESC;
```

실제 출력에서 board 목록 쿼리가 그대로 잡혔다:

```
쿼리: SELECT b.idx, b.title, b.content ...   (게시글 목록)
  실행횟수 15  │  반환행 300  │  검사행 624,543
  검사/반환 배율: 2,082          ← 300행 주려고 62만 행을 읽음
  디스크임시 3  │  정렬스캔 3  │  인덱스미사용 3
```

### 쓸 수 있는 신호

| 지표 | 의미 |
|---|---|
| **검사행 / 반환행 배율** | 20행 주려고 5만 행을 읽으면 2,500배. **가장 강력한 단일 지표** |
| `SUM_CREATED_TMP_DISK_TABLES` | 디스크 임시테이블 — 확실한 적신호 |
| `SUM_SORT_SCAN` | 정렬을 위해 전체를 훑음 |
| `SUM_NO_INDEX_USED` | 인덱스 없이 실행됨 |

### ⚠️ 한계: 오탐이 있다

실제 스캔에서 **1등이 정합성 검증 쿼리**(`verify-data-integrity.sql`, 검사/반환 152,769배)였다.
전체 집계 쿼리는 원래 많이 읽는 게 정상이다. 통계 배치도 마찬가지다.

**그래서 이건 자동 알람이 아니라 "어디가 아픈지 찾는 레이더"다. 사람이 보고 판단해야 한다.**

## 5. 제안 구조 — 2층

### Layer 1 · 레이더 (넓게, 자동)

`performance_schema` digest 를 주기적으로 스캔해 이상 쿼리 목록을 뽑는다.

- **설정 0.** 프로젝트 전체 쿼리를 자동 커버. 새 쿼리가 생겨도 자동 포착
- 출력은 **후보 목록**이며, 사람이 판단한다
- 오탐(집계/배치 쿼리)은 제외 목록으로 관리

### Layer 2 · 가드레일 (좁게, 정밀)

레이더로 찾아낸 **진짜 문제 쿼리**에만 회귀 방지 가드를 건다. **여기가 추상화 대상이다.**

```java
interface QueryPlanGuard {
    String name();                 // 메트릭 태그
    Set<Violation> forbidden();    // FILESORT / TEMP_DISK / FULL_SCAN / RATIO
    long minRowsToVerify();        // 이 아래면 검증이 무의미하므로 생략
}
```

도메인별 구현체를 만들고, 스케줄러가 `List<QueryPlanGuard>` 를 주입받아 순회한다.
**이것이 진짜 다형성이다.** 현재 `BoardListQueryPlanMaintainer` 는 이 인터페이스의 첫 구현체가 된다.

### 별개 관심사 — 통계/히스토그램 유지보수

"어떤 테이블의 어떤 컬럼에 히스토그램이 필요한가" 는 쿼리별 가드와 **다른 관심사**다.
선언 목록(`(table, columns)`)을 모아 중복 제거 후 `ANALYZE` 를 돌리는 별도 컴포넌트가 맞다.

## 6. 구현 전에 풀어야 할 설계 문제 3개

### (a) 🔴 체크 쿼리가 리포지토리와 갈라지는 문제

SQL 을 복붙하면 사본이 된다(§2.2). 후보:

1. Hibernate `StatementInspector` 로 **실제 나가는 SQL 을 캡처** → 그것을 `EXPLAIN`
   - **막히는 지점**: 캡처한 SQL 은 `?` 플레이스홀더다. `EXPLAIN` 하려면 파라미터가 바인딩되어야 한다
2. `EXPLAIN FOR CONNECTION <id>` — 다른 커넥션에서 실행 중인 쿼리를 설명
   - 실행 중인 순간을 잡아야 해서 스케줄러 방식과 안 맞는다
3. **`EXPLAIN` 을 포기하고 Layer 1 의 실측 지표로 대체**
   - `digest` 에 이미 `디스크임시 / 정렬스캔 / 검사배율` 이 기록된다
   - **쿼리 문자열을 들고 있을 필요가 사라진다** → (a) 문제가 원천 소멸
   - 대신 "계획이 어떻게 생겼는지"는 못 본다. 증상만 본다

> **3번이 가장 유력해 보인다.** 사본을 만들지 않는 유일한 길이다.
> 다만 "증상 감지"와 "원인 진단"은 다르므로, 원인 파악은 사람이 `EXPLAIN` 으로 하는 것으로 나눈다.

### (b) "나쁜 계획"의 정의가 쿼리마다 다르다

`Using filesort` 가 항상 나쁜 것은 아니다. 작은 결과셋 정렬은 저렴하다.
관리자 통계 쿼리의 풀스캔은 정상이다.

**금지 신호를 쿼리별로 선언**해야 한다. 전역 규칙 하나로는 안 된다.

### (c) 검증 없는 가드는 헛돈다 (2026-07-13 에 배운 것)

각 가드마다 **"히스토그램/인덱스를 없애면 실제로 그 신호가 나타나는지"** 를
CI 에서 먼저 확인해야 한다. 그게 없으면 가드가 아무것도 지키지 못한 채 초록불만 켠다.

(`BoardListQueryPlanMaintainerTest` 의 2단계 구조가 이 원칙의 첫 사례다.)

## 7. 제안하는 순서

```
1. Layer 1 (digest 스캐너)로 전체 쿼리를 한 번 훑는다     ← 몇 개인지 "센다"
2. 실제 문제 쿼리 목록 확보 (N = ?)
3. 그 N개를 보고 Layer 2 추상화를 설계한다               ← N=1이 아니라 실측치에서
4. 각 가드에 CI 2단계 테스트 (필수)
5. 그 과정에서 board Maintainer 의 SQL 복붙 문제(§6-a)도 함께 해소
```

**핵심: 몇 개인지 모르면 어떤 추상화가 맞는지도 모른다.**
지금 추상화하면 board 하나에 맞춘 껍데기만 나온다.

---

## 8. 아직 확인하지 않은 것

- **프로젝트 전체에 이런 쿼리가 몇 개인가** — 1단계의 목적이다. 현재는 board 목록 1건만 확인됨
- `tmp_table_size` 를 올리는 것이 답인가 — 아니다. 디스크 I/O 를 메모리 낭비로 바꿀 뿐,
  근본 원인(잘못된 계획)은 그대로다. 계획을 고치면 임시테이블 자체가 안 생긴다
- **`carerequest` 주변 검색에 공간 인덱스 없음** (별건, baseline 문서 §4 참고)
- **`file.idx_file_target`** 미측정 (시드가 file 테이블을 만들지 않음)
