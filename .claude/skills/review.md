# Code Review Skill

## 트리거

사용자가 코드 리뷰, 점검, 검토를 요청할 때 실행한다.

## 경계 (먼저 확정)

```
review        코드를 읽고 의심 지점을 찾는다          ← 이 스킬
db-review     JPA/Repository 변경의 DB 관점 점검      ← DB 쪽 심화가 필요하면
db-diagnose   재현·계측으로 실제 문제를 증명한다       ← 측정이 필요해지면
test          결함을 잡는 테스트로 고정한다            ← 검증이 필요해지면
```

읽어서 **"의심된다"까지가 이 스킬의 끝**이다. "느리다/깨진다"를 단정하려면 넘긴다.

## ⚠️ 이 문서 사용법 — 목록은 체크리스트가 아니다

리뷰의 중심은 **"이 코드가 약속한 일을 실제로 하는가"** 다. 규칙 대조가 아니다.
- §3의 Petory 신호 목록은 **점화용(priming)** 이다. 목록만 대조하고 "문제없음"으로 끝내면 **실패다.**
- 목록에 없는 문제도 약속을 깨면 **심각도 그대로** 보고한다(목록 밖이라고 Info로 깎지 않는다).
- 확인 안 한 축은 "문제없음"이 아니라 **"미확인"** 이다.

## 범위 파악

- 사용자가 지정한 파일/도메인/PR 범위를 확인한다.
- 범위가 없으면 최근 변경(`git diff --name-only HEAD~1`)을 대상으로 한다.
- 원격과 비교하기 전에 `git fetch` — `origin/...` 은 로컬 캐시다.

---

## 1. 루프

```
① 약속 고정    바뀐 메서드마다 "호출자에게 무엇을 약속하나"를 먼저 적는다 (§2 ⓪)
② 질문 생성    약속 + 4축으로 심문 (§2)
③ 근거 확인    "안전하다"는 주장마다 확인 경로를 찾는다 — 못 찾으면 추정 (§4)
④ 분류        깨지면 누가 무엇을 잃나로 등급을 정한다 (§5)
⑤ 인계        측정 → db-diagnose, 검증 → test
```

**①을 건너뛰면 리뷰가 아니라 대조다.** 약속을 모르면 무엇이 깨졌는지 판단할 기준이 없다.

---

## 2. 질문 생성 — 약속 + 4축

### ⓪ 약속 (정확성) — 가장 먼저

메서드마다 한두 문장으로 쓴다. 이름이 아니라 **동작**으로.

```
성공하면   무엇이 참이 되나        (예: 회원이 생기고, 인증 상태가 맞게 적용된다)
실패하면   무엇이 남나 / 안 남나   (예: 아무 일도 없었던 것처럼 된다)
호출자는   무엇을 믿고 쓰나        (예: 반환된 DTO의 id로 바로 로그인 가능)
```

그다음 **약속이 깨지는 상황을 스스로 찾는다:**

| 방향 | 자문 (씨앗 — 전부 아님) |
|---|---|
| 입력 경계 | null·빈 값·최대 길이·음수·중복 값이면? 다른 칸끼리 조합이 겹치면? |
| 실패 경로 | 중간 줄에서 예외가 나면 그 전에 한 일은 되돌아가나? **되돌릴 수 없는 일(메일·HTTP·Redis·파일·메시지)이 커밋 전에 있나?** |
| 동시 요청 | 같은 요청이 두 번 동시에 오면? 읽고→판단→쓰기 사이에 다른 요청이 끼면? |
| 순서·시점 | 이 일이 일어나는 시점이 약속과 맞나? (커밋 전/후, 비동기 완료 전/후) |
| 호출자 기대 | 호출처를 전부 찾아봤나? 그들이 기대하는 것과 지금 동작이 같은가? |

### ①~④ 변경 위생

| 축 | 던지는 질문 | 놓치기 쉬운 신호 (예시 — 전부 아님) |
|---|---|---|
| **① 범위** | 요청한 것만 바뀌었나? **더 했나** / **덜 했나**(같은 결함의 형제 호출처 방치) | 1구현 인터페이스, 안 쓰는 확장 포인트, 지목된 경로만 수정 |
| **② 파급** | 이 변경을 쓰는 다른 곳은? 계약(시그니처·응답·스키마·설정 키)이 바뀌었나? | 남은 호출처, 응답 필드 이름 변경, 엔티티↔Flyway 불일치(`ddl-auto=validate`가 기동 실패) |
| **③ 근거** | "안전하다/안 쓰인다/빨라졌다/동작 같다"가 확인인가 추정인가? | 전수 검색 없이 "안 쓰인다", 실행 없이 "동작 동일", 측정 없이 수치 |
| **④ 일관성** | 이미 있는 걸 다시 만들지 않았나? 이웃 코드·기존 결정과 맞나? | 기존 헬퍼 재구현, `toDTOList` 있는데 `Page.map(toDTO)`, 다른 리스너와 다른 패턴 |

> **규칙**: ⓪~④ 각각 "확인함/미확인"을 명시한다.

## 3. Petory 신호 — 점화용 (닫힌 목록 아님)

이 저장소에서 실제로 사고가 났거나 규칙으로 정한 모양들이다. §2로 질문을 만든 **뒤에** 빠진 게 없는지 훑는 용도다.

| 영역 | 신호 | 왜 문제인가 |
|---|---|---|
| JPA/쿼리 | `@ManyToOne`/`@OneToOne`에 `fetch = LAZY` 없음 | 기본 EAGER → 목록 N+1 |
| JPA/쿼리 | 루프 안 컬렉션 접근, `Page.map(converter::toDTO)` | 행마다 단건 조회 → N+1 (`toDTOList` 사용) |
| JPA/쿼리 | 커스텀 쿼리에 소프트 삭제 조건 누락 | 탈퇴·삭제 행이 섞여 나옴 |
| JPA/쿼리 | `LIKE '%…%'`, 페이징 없는 `findAll()` | 풀스캔 / 전량 로딩 |
| 트랜잭션 | `@Transactional` 안에서 되돌릴 수 없는 일 (`@Async`여도) | 커밋 실패 시 메일·Redis만 남음 → `AFTER_COMMIT` 리스너로 (예: `UserRegisteredEventListener`) |
| 트랜잭션 | `this.method()`로 `@Transactional` 호출, private에 `@Transactional` | 프록시를 안 타서 트랜잭션 무시 |
| 동시성 | 금액·수량·포인트 변경 | 비관적 락(`findByIdForUpdate`) 또는 원자적 UPDATE 필요 |
| 동시성 | 읽고→판단→쓰기 (중복 검사 후 저장 등) | TOCTOU — DB UNIQUE 또는 락으로 마무리했나 |
| 보안 | 데이터 변경 API 권한 검사, Response DTO에 비밀번호·토큰 | 권한 우회 / 민감정보 노출 |
| 보안 | 남의 리소스 ID로 접근 가능한가 | IDOR — 소유자 검사 |
| 품질 | `System.out.println`, 미사용 import | 노이즈 |

## 4. 근거 등급

| 등급 | 뜻 | 표기 |
|---|---|---|
| **확인** | 실행·전수검색·실제 출력으로 봤다 | 근거(명령·결과)를 함께 적는다 |
| **추정** | 읽어서 그럴 것 같다 | "추정"이라고 쓰고 넘길 스킬을 지정 |
| **미확인** | 안 봤다 | "문제없음"으로 쓰지 않는다 |

> 읽어서 나오는 지적은 대부분 **추정**이다. 정상이다. 추정을 확인처럼 쓰는 게 문제다.
> 예: "메일이 느려서 트랜잭션을 잡는다"는 추정이었고 틀렸다 — `@Async`였다. 메서드 정의를 열어보는 게 확인이다.

---

## 5. 심각도 — 깨지면 누가 무엇을 잃나

| 등급 | 기준 |
|---|---|
| 🔴 **Critical** | 돈·데이터 정합성·보안이 깨진다. 또는 약속이 정상 경로에서 깨진다 |
| 🟡 **Warning** | 드문 조건(경계값·동시성·실패 경로)에서 약속이 깨진다. 성능 저하 의심 |
| 🟢 **Info** | 약속은 지켜지나 읽기·유지보수 비용. 요청 범위 밖이면 **범위 밖**이라고 명시 |

실제 위험이 작으면 작다고 쓴다(예: "IDENTITY라 INSERT가 save 시점에 나가 커밋 실패만 남는다 — 드묾"). 부풀리지 않는다.

## 6. 산출물 형식

```
## 요약
한 단락. 무엇이 바뀌었고, 가장 위험한 지점 하나.

## 약속
- `UsersService.createUser` — 성공: … / 실패: … / 호출자: …

## 이슈
### 🔴 Critical
#### 제목
- 위치: `파일:줄`
- 약속: 이 메서드는 ___ 를 약속한다
- 깨지는 상황: ___ 일 때
- 결과: ___ (누가 무엇을 잃나)
- 근거 등급: 확인 / 추정 / 미확인 (확인이면 근거)
- 수정안: 구체적 코드 또는 방법

### 🟡 Warning / 🟢 Info
(동일 형식)

## 축 확인
| 축 | 결과 | 비고 |
|---|---|---|
| ⓪ 약속 | 확인 / 미확인 | |
| ① 범위 | 확인 / 미확인 | |
| ② 파급 | 확인 / 미확인 | |
| ③ 근거 | 확인 / 미확인 | 추정으로 남은 주장 N개 |
| ④ 일관성 | 확인 / 미확인 | |

## 잘된 점
- 약속을 지키기 위해 잘 처리한 지점

## 판정
Critical 0 → "✅ 커밋 가능" / 1개 이상 → "🔴 수정 필요"
인계: 측정 → db-diagnose / 검증 → test
```

---

## 워크플로우 연계

- Critical ≥ 1 → `/fix`(버그) 또는 `/refactor`(구조·성능) → `/test` → `/commit`
- Critical 0 → `/test` → `/commit`

## 제약

- **리뷰만 한다.** 사용자 확인 없이 코드를 수정하지 않는다. "수정할까?" 확인 후 동의하면 적용하고 `/test`를 제안한다.
- 목록을 체크리스트로 소비하지 않는다 — 약속에서 질문을 **생성**한다.
- 추정을 확인처럼 쓰지 않는다(§4). 확인 못 한 축은 "미확인".
- 지적마다 **구체적 수정안**을 쓴다. "개선 필요"만 쓰지 않는다.
- 기존 아키텍처 패턴을 존중한다 (프로젝트 컨벤션 > 일반 베스트 프랙티스).
