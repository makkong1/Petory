# DB Diagnose Skill — 원인분석 → 검증 → 해결

정적 리뷰(`db-review`)가 "코드에 문제가 있나 훑기"라면, 이건 **측정으로 실제 문제를 잡아내는** 능동 진단이다.
전제 문서: `docs/interview/concepts/면접/24_측정도구_실행계획_기초.md`(도구), `23_쿼리_옵티마이저_통계와_실행계획.md`(통계).

> **철학 (반드시 지킴)**: ① 손으로 쓴 SQL 말고 **앱이 실제 날린 쿼리**를 본다. ② 하나로 재지 말고 **2개 이상으로 교차검증** — 두 값이 어긋나는 지점이 곧 발견 지점이다. ③ 측정 안 한 건 "문제없음"이 아니라 **"미측정"**이다. ④ "고쳤더니 빨라졌다"는 증거가 아니다 — **인과를 증명**한다.

---

## 0. 진단 루프 (모든 DB 문제 공통)

```
① 증상 → 의심       어떤 메서드/패턴이라 무슨 문제가 예상되나 (§1 표)
② 재현              실데이터 규모 시드 + 앱 기동 + curl (SQL 손으로 X)
③ 계측              문제 유형에 맞는 도구 선택 (§2 표)
④ 교차검증          도구 2개 이상 — 불일치 = 함정 발견 (§3 표)
⑤ 원인 특정         EXPLAIN ANALYZE 예상 vs 실제 / 통계 / 락
⑥ 해결 후보 + 트레이드오프   여러 방법 나열, 성능만으로 결정 X (§4 표)
⑦ 인과 증명         적용→제거→재적용(A/B/A), before는 worktree 구코드 실제 실행
⑧ 회귀 방지         테스트가 "결함을 실제로 잡는지" 먼저 확인 (§5)
```

각 단계에서 **"내가 지금 뭘 못 보고 있나"**를 먼저 묻는다. 이 스킬의 값어치는 ③④에 있다.

## 1. 증상 → 의심 (메서드만 보고 무슨 문제를 예상하나)

| 메서드/코드 패턴 | 예상 문제 | 왜 |
|---|---|---|
| `Page<T>` 반환 목록 조회 | **자동 COUNT 쿼리** | 목록 SELECT 옆에 총건수 COUNT가 같이 나감. `countQuery` 미지정 시 목록 JOIN을 그대로 뭄 → 숨은 풀스캔 |
| 목록 조회 후 DTO 변환에서 연관 접근 | **N+1** | LAZY·Converter 내부 접근·루프 안 Repository 단건 호출 |
| `Page.map(converter::toDTO)` | **N+1** | 단건 변환기를 행마다 호출. `toDTOList`(배치) 있으면 그걸 써야 함 |
| `WHERE`/`ORDER BY` 컬럼에 인덱스 없음 | **filesort / 풀스캔** | 특히 정렬 인덱스가 있는데도 옵티마이저가 안 쓰면 → **통계/히스토그램** 의심(§23) |
| OFFSET 페이징(깊은 페이지) | **선형 저하** | LIMIT은 정렬 뒤 적용 → 앞 N행 만들고 버림. 1페이지도 손해볼 수 있음 |
| 저카디널리티 컬럼(`status`,`is_deleted`,`type`) 필터가 조인 순서 좌우 | **선택도 오판** | 인덱스로 못 잡음 → 히스토그램 필요 |
| 동시 접근 자원(잔액·인원·카운트) | **Lost Update / 정원초과 / 데드락** | 원자 UPDATE·비관적 락·락 순서 문제 |
| 대량 적재를 한 트랜잭션 | **부분실패 전체롤백 / 세션 오염** | 배치 분리 + `REQUIRES_NEW` 필요 |
| 첨부/파일 `(target_type, target_idx)` 조회 | **복합 인덱스 누락 풀스캔** | 쿼리 수를 줄여도(N+1 해결) 스캔량은 그대로일 수 있음 — 다른 축 |

## 2. 문제 유형 → 계측 도구 (원인을 뭘로 보나)

| 알고 싶은 것 | 1차 도구 | 교차검증 |
|---|---|---|
| 앱이 진짜 날린 쿼리 | 앱 기동 + `curl` + `spring.jpa.show-sql=true` | — (여기가 기준점) |
| 쿼리 **개수**(N+1) | `grep -c 'Hibernate:' 로그` | Hibernate `Statistics` |
| 진짜 DB **왕복** 수 | `getPrepareStatementCount()` | `getQueryExecutionCount()` (LAZY 누락 — 함정) |
| 어떤 쿼리가 **비쌌나** | `performance_schema` digest **3기준**: ①`SUM_ROWS_EXAMINED`(풀스캔·COUNT) ②`COUNT_STAR`(N+1) ③쓰기(과잉락) | `EXPLAIN ANALYZE` |
| 계획이 **왜** 나쁜가 | `EXPLAIN ANALYZE` (예상 rows vs actual rows, `loops`, filesort/temporary) | `EXPLAIN FORMAT=JSON` |
| 인덱스 있는데 **왜 안 쓰나** | 옵티마이저 **통계/히스토그램** (§23) | `ANALYZE TABLE` 후 계획 재확인 |
| **락** 경합 | `Innodb_row_lock_waits` / `Innodb_row_lock_time` (전역) | `SHOW ENGINE INNODB STATUS` |

> **N+1은 검사행순으로는 안 보인다.** 값싼 쿼리가 수백 번 반복돼 각각은 싸기 때문 — 반드시 **호출횟수순(②)**으로도 봐야 한다.

## 3. 측정 함정 (이걸 모르면 오진한다 — 이 스킬의 핵심)

| 함정 | 무슨 일이 벌어지나 | 대응 |
|---|---|---|
| **조인이 카운트를 줄인다** | `JOIN FETCH`·`@BatchSize`가 N개 LAZY 로딩을 IN 쿼리 1개로 접음 → "쿼리 수"만 보면 문제가 사라진 것처럼 보이거나 실제보다 적게 잡힘 | 쿼리 **개수**와 **검사 행수/스캔량**을 **따로** 본다. 개수↓라도 스캔량은 그대로일 수 있음 |
| **`getQueryExecutionCount` 과소보고** | JPQL만 세고 LAZY 로딩 조회를 안 셈 → 이 값만 보면 `JOIN FETCH`가 불필요해 보여 최적화를 **되돌릴 뻔** | 진짜 왕복은 `getPrepareStatementCount()` |
| **Hibernate `Statistics` 절반 보고** | 파생 쿼리·lazy 초기화 미집계 → 실제 41개를 **21개로** 보고(Chat N+1 사례) | 최종 카운트는 **SQL 로그 grep** |
| **`SUM_LOCK_TIME`이 행 락 미포착** | 테이블 락만 셈 → InnoDB 행 락(비관적 락)을 **0으로** 보고 → "락 대기 없음" 오판(대기 377회인데 0) | `Innodb_row_lock_*` 전역 카운터 |
| **Gradle `UP-TO-DATE` 스킵** | DB 상태는 Gradle 입력이 아니라 인덱스/통계를 바꿔도 소스가 같으면 옛 결과로 통과 | `cleanTest` 또는 `--rerun-tasks` |
| **손으로 쓴 SQL로 재기** | 앱이 실제 붙이는 COUNT·조인·컬럼(예: `content` LONGTEXT)을 빠뜨려 비용이 달라짐 | 앱 기동 + curl로 **실제 쿼리** |
| **작은 픽스처** | 100~500행에선 어떤 계획을 골라도 차이 없음 → 인덱스·계획 문제가 아예 안 나타남 | 실데이터 규모 시드(예: board 5만) — 단 N+1은 규모 무관 |
| **에러를 `2>/dev/null`로 숨김** | 재현 실패(FK로 TRUNCATE 실패 등)를 못 보고 "재현 안 됨" 오결론 | 에러를 드러내 놓고 측정 |

## 4. 해결 후보 카탈로그 (성능만으로 결정하지 않는다)

| 문제 | 후보들 | 트레이드오프 |
|---|---|---|
| N+1 (`@ManyToOne`) | `JOIN FETCH` / `@EntityGraph` | 행 안 늘어 안전 |
| N+1 (컬렉션 `@OneToMany`) | ID를 `IN`으로 묶어 **배치 조회** 후 `Map` 병합 | JOIN FETCH하면 카티전 곱 뻥튀기 → 배치가 맞음 |
| 자동 COUNT 비쌈 | `countQuery` 분리 / `Slice`(총건수 불필요 시) / 상태 컬럼 비정규화로 조인 제거 | Slice는 "맨 뒤" UI 못 함 |
| 깊은 페이지 | 키셋(커서) / **지연조인**(커버링 인덱스로 ID만 → 20건만 조인) | 키셋 최고성능이나 페이지번호·맨뒤 점프 UI 못 지원 → 지연조인 택 |
| 인덱스 있는데 filesort | 행수 `ANALYZE` → 그래도면 **히스토그램**(§23) | 코드·인덱스 추가 0. 단 조용히 회귀 → EXPLAIN 재검증 필요 |
| 인원/카운트 동시성 | 조건부 원자 UPDATE(`SET c=c+1 WHERE c<max`) | 현재값 검증 불필요할 때. 락 안 끌고 감 |
| 잔액 동시성 | 비관적 락(`findByIdForUpdate`) | "부족" 분기 태우려면 현재값 읽어야 함 |
| 데드락 | **락 획득 순서 통일**(X락 먼저 선점) | 같은 트랜잭션이면 순서만 바꿔도 정합성 동일 |
| 대량 적재 | 배치 단위 + `REQUIRES_NEW` 트랜잭션 분리 + 컨텍스트 clear | 부분실패 격리 |

## 5. 검증 — "통과하는 테스트"가 아니라 "결함을 잡는 테스트"

- [ ] **before는 재구성이 아니라 실제 구코드**로: git worktree로 이전 커밋을 띄워 재측정(추정 금지).
- [ ] **A/B/A 인과 증명**: 적용→제거(되돌아옴 확인)→재적용. 개선 사실만으론 인과가 안 잡힘.
- [ ] **테스트가 결함을 실제로 잡는지 먼저**: 수정 코드를 되돌린 상태에서 테스트가 **빨간불**인지 확인 → 그 다음 초록불. 이 앞단이 없으면 "통과만 하는" 테스트다.
  - 예: 경고 동시성 테스트가 `경고수==기록수`(같은 트랜잭션 두 값)를 비교해 버그가 있어도 항상 통과하던 사례 → `성공콜수==최종경고수`로 강화.
- [ ] **동시성은 curl로 관측 불가** → `petory_test`에서 `CountDownLatch` + 트랜잭션 우회로 결정론적 재현.
- [ ] 측정 못 한 범위는 결과에 **"미측정"**으로 명시(COUNT 일부, 시드 없는 도메인 등).

## 산출물 형식

```
## 원인 분석
- 증상: (무엇이 느린가/틀리나)
- 의심: (§1 어느 패턴 → 무슨 문제)
- 계측: (§2 어느 도구로 봤나)
- 교차검증: (도구 2개 결과 — 어긋났다면 §3 어느 함정)
- 원인 특정: (EXPLAIN ANALYZE 예상 N vs 실제 M / 통계 / 락 — 증거)

## 검증 방법
- 재현: 시드 규모 + curl / 동시성이면 Latch
- 인과: A/B/A 결과

## 해결 방법
- 후보 + 트레이드오프 (§4), 택한 이유(성능만 아님)
- 회귀 방지: 결함 잡는 테스트(빨간불 먼저 확인)
```

---

## 워크플로우 연계
- 진단 완료 → 수정은 `/refactor`(구조·성능) 또는 `/fix`(버그) → `/test`(회귀) → `/commit` → `/docs`.
- 정적 훑기가 먼저 필요하면 `db-review`, 능동 재현·계측이면 이 스킬.

## 제약
- 추측으로 결론 내지 않는다 — 앱이 실제 날린 쿼리와 도구 2개로 확인한 뒤 쓴다.
- 도구를 믿기 전에 도구부터 의심한다(§3). 한 도구 숫자만으로 개선/롤백 결정하지 않는다.
- 부풀리지 않는다. 수치엔 측정 조건(주 지표=쿼리 수, 시간 보조, 시드 규모)을 함께 적는다.
